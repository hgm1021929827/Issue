下列前提若不同意，請在對應題目選「自行補充」：

## 三、待確認項目



### Q1：一次匯入綁哪一筆專案



#### 問題描述

來源 5.1 是「先填本次所屬專案再匯入」，語意是**一份檔對一筆專案**。第三階段已能在畫面新增專案。Excel 裡也可能再出現專案編號／代號。本輪要以哪種方式對上第三階段的專案？

#### 推薦方案 A：先選（或新建）既有專案，再上傳該專案的 Excel

說明：匯入入口在專案詳情或清單「匯入」。檔案內容寫入**目前選中的專案**。Excel 內代號若與目前專案不一致則整批失敗並提示，不自動改掛別筆。


| 面向   | 說明                                   |
| ---- | ------------------------------------ |
| 推薦原因 | 對齊 5.1「本次所屬專案」；不依賴廠商也能開始；與第三階段手動建檔銜接 |
| 優點   | 不會因 Excel 多代號而建出幽靈專案；異常跳轉目標清楚        |
| 缺點   | 不能一份檔一次灌多個專案                         |
| 開發成本 | **中**。單專案上傳＋寫入該專案的議題與工時              |
| 維護成本 | **低**。一次匯入一個容器，之後較好比對                |




#### 其他可選方案

**方案 B：只靠 Excel 內代號自動對應；沒有就新建專案**


| 面向   | 說明                      |
| ---- | ----------------------- |
| 優點   | 少一步選專案                  |
| 缺點   | 無廠商時新建專案欄位不完整；代號填錯會建錯專案 |
| 開發成本 | **中**。多自動建檔與對應規則        |
| 維護成本 | **中**。錯檔難以追             |


**方案 C：一份檔可含多專案，依列上的專案編號拆開**


| 面向   | 說明                        |
| ---- | ------------------------- |
| 優點   | 批次效率高                     |
| 缺點   | 超出 5.1「本次所屬專案」；異常跳轉與結果頁複雜 |
| 開發成本 | **高**。多專案交易與部分成功策略        |
| 維護成本 | **高**                     |




#### 建議選擇

> 建議選擇 **A**。

原因：來源就是一次一個專案；第三階段已有專案主檔。先選專案再上傳最不容易灌錯。

#### 使用者選擇

☑ A — 先選既有專案再上傳（推薦）

□ B — 依 Excel 代號自動對應或新建

□ C — 一份檔拆多個專案

□ 自行補充

### Q2：沒有廠商、沒有成員時，匯入還做不做篩選



#### 問題描述

來源：匯入前必選廠商；「工作項目」依負責人員、「議題單」依處理人過濾。本輪不做廠商與成員。若不略過這兩點，本階段無法開始匯入。

#### 推薦方案 A：不選廠商、不依人員過濾；工作表裡有的列都進目前專案

說明：廠商、負責人員、處理人欄若出現在 Excel，本輪讀了也不用來擋匯入（可列入「未使用欄」或不顯示）。整張「工作項目」「議題單」有效列都對目前專案處理。


| 面向   | 說明                             |
| ---- | ------------------------------ |
| 推薦原因 | 階段範圍已排除成員／廠商；個人單機本來就是「這台電腦上的我」 |
| 優點   | 本輪就能匯入；之後做成員再加篩選，不擋現在          |
| 缺點   | 若你習慣一份 Excel 含多人列，會把別人的列也灌進來   |
| 開發成本 | **低**。少兩層主檔與過濾                 |
| 維護成本 | **低**。之後篩選可當增量，不拆契約            |




#### 其他可選方案

**方案 B：匯入畫面加兩個可選文字框（負責人員、處理人），有填才過濾，比對 Excel 欄位字串**


| 面向   | 說明                    |
| ---- | --------------------- |
| 優點   | 接近 6.1／6.2，仍不必做成員主檔   |
| 缺點   | 姓名拼字不一致就濾不到；不是真正的成員關聯 |
| 開發成本 | **中**。多過濾與空值規則        |
| 維護成本 | **中**。做成員後這兩個框可能作廢    |


**方案 C：本輪仍做客戶公司下拉＋快捷新增（來源 5.2），人員篩選仍不做**


| 面向   | 說明                     |
| ---- | ---------------------- |
| 優點   | 對齊匯入前置必填廠商             |
| 缺點   | 把「再下一階段」的客戶公司拉進本輪，範圍膨脹 |
| 開發成本 | **中**。新主檔與專案加欄         |
| 維護成本 | **中**。之後窗口／聯絡資料還要再擴    |




#### 建議選擇

> 建議選擇 **A**。

原因：你已同意本輪不含成員與廠商。個人使用下「整表進目前專案」最乾淨；多人 Excel 可之後再篩。

#### 使用者選擇

□ A — 不廠商、不人員過濾，整表進目前專案（推薦）

☑ B — 可選姓名文字過濾，仍無成員主檔

### Q3：「工作項目」工作表對應什麼



#### 問題描述

來源：檔必須有「工作項目」且含專案工作項目；「議題單」才是專案議題（項次）。第三階段沒有第三種「工作包」實體。工作項目列是更新**專案本體**（日期、備註工時），還是每一列都要變成某種明細？

#### 推薦方案 A：工作項目用來更新「目前這筆專案」的預計日與日期工時；多列則依日期合併工時

說明：預計開始／完成取工作表上有值的欄（衝突見 Q7）。備註欄逐日解析後，**同一日多列工時相加**寫入該專案的日期工時。不因工作項目列新增專案議題。專案議題只來自「議題單」。


| 面向   | 說明                           |
| ---- | ---------------------------- |
| 推薦原因 | 對齊「工作項目＝專案、議題單＝專案議題」；不必發明新實體 |
| 優點   | 與第八章專案工時比對直接對得上              |
| 缺點   | 若你其實把工作項目當多筆 WBS，本輪會壓成一筆專案   |
| 開發成本 | **中**。解析備註＋合併寫入專案工時          |
| 維護成本 | **低**。之後真要 WBS 再加實體          |




#### 其他可選方案

**方案 B：工作項目每一列建成獨立「工作項目」實體（不是專案議題）**


| 面向   | 說明                        |
| ---- | ------------------------- |
| 優點   | 保留列級資料                    |
| 缺點   | 本輪多一種主檔；來源未要求與議題單並列的第三種畫面 |
| 開發成本 | **高**。新實體、清單、比對、跳轉        |
| 維護成本 | **高**                     |


**方案 C：工作項目列若帶項次就當專案議題，與議題單合併**


| 面向   | 說明                |
| ---- | ----------------- |
| 優點   | 少一種對應             |
| 缺點   | 兩張表語意混在一起，和來源分表相反 |
| 開發成本 | **中**             |
| 維護成本 | **高**             |




#### 建議選擇

> 建議選擇 **A**。

原因：來源用兩張表區分專案與專案議題。第三階段也是這兩個實體。

#### 使用者選擇

□ A — 工作項目只更新專案本體，工時依日合併（推薦）

☑ B — 每一列新做成工作包實體

□ C — 工作項目與議題單都寫入專案議題

### Q4：議題單列與既有專案議題怎麼對



#### 問題描述

第三階段專案議題以「同一專案內項次」唯一。再次匯入同一檔時：更新、新增、刪網頁多出來的列，各要不要做？

#### 推薦方案 A：依項次新增或更新；網頁多出來的列不刪

說明：Excel 有、網頁無 → 新增。兩邊都有 → 更新標題、內容、分類若有對應、預計日、該列日期工時。網頁有、Excel 無 → **留下**，只在匯入結果註記「網頁多出項次 x」（可選，不強制當錯誤）。


| 面向   | 說明                  |
| ---- | ------------------- |
| 推薦原因 | 避免匯入把畫面上手補的議題刪掉     |
| 優點   | 可重複匯入；手改與匯入可並存      |
| 缺點   | 過期項次會留在網頁，要自己刪      |
| 開發成本 | **中**。upsert＋工時覆寫規則 |
| 維護成本 | **低**               |




#### 其他可選方案

**方案 B：Excel 當完整真相；網頁有但 Excel 沒有的項次刪除**


| 面向   | 說明             |
| ---- | -------------- |
| 優點   | 匯入後與檔完全一致      |
| 缺點   | 容易誤刪手建列        |
| 開發成本 | **中**          |
| 維護成本 | **中**。要很強的確認文案 |


**方案 C：只新增、既有項次不更新**


| 面向   | 說明             |
| ---- | -------------- |
| 優點   | 不覆蓋手改          |
| 缺點   | 工時比對會永遠對到舊網頁資料 |
| 開發成本 | **低**          |
| 維護成本 | **高**。比對失真     |




#### 建議選擇

> 建議選擇 **A**。

原因：重複匯入是為了補 Excel、對工時，不該當「整包覆蓋刪除」。

#### 使用者選擇

☑ A — 項次 upsert，不刪網頁多的列（推薦）

□ B — Excel 沒有的項次從網頁刪掉

□ C — 只新增不更新

### Q5：日期工時在網頁要不要能手改



#### 問題描述

第七章、第八章都假設網頁有「日期工時」。只有匯入寫入、不能手改的話，來源說的「網頁有、Excel 還沒記」很難發生（除非先前匯入過）。標記完成取最後一筆工時也需要這份資料。

#### 推薦方案 A：專案與專案議題都有日期工時明細；可在詳情手增／改／刪；匯入會寫入或更新同一日

說明：一列＝一個日期＋小時數（可小數）。同一主檔同一日只能一列。匯入解析到同一日則更新小時（或依 Q3 合併後寫入）。畫面上可補 Excel 還沒有的那天。


| 面向   | 說明                             |
| ---- | ------------------------------ |
| 推薦原因 | 比對與實際起迄都建立在這張明細上               |
| 優點   | 不匯入也能記工時；異常情境（網頁有 Excel 無）自然出現 |
| 缺點   | 詳情頁多一塊編輯                       |
| 開發成本 | **中**。明細 CRUD＋匯入寫入             |
| 維護成本 | **中**。要維持「一日一列」                |




#### 其他可選方案

**方案 B：工時只存在「上次匯入快照」，畫面不能手改**


| 面向   | 說明                           |
| ---- | ---------------------------- |
| 優點   | 畫面單純                         |
| 缺點   | 第七章實際日起算與「網頁有 Excel 無」幾乎做不出來 |
| 開發成本 | **低**                        |
| 維護成本 | **高**。之後仍要補手改                |


**方案 C：本輪只做比對、不落日期工時表（每次匯入只跟 Excel 自己比）**


| 面向   | 說明                 |
| ---- | ------------------ |
| 優點   | 最小                 |
| 缺點   | 沒有網頁側工時，第八章四種異常做不完 |
| 開發成本 | **低**              |
| 維護成本 | **高**。等於沒做來源第八章    |




#### 建議選擇

> 建議選擇 **A**。

原因：工時比對的一邊必須是網頁持久化資料。手改才能反映「Excel 還沒跟上」。

#### 使用者選擇

☑ A — 專案與專案議題都有可手改的日期工時（推薦）

□ B — 只有匯入快照，不能手改

□ C — 本輪不存日期工時

□ 自行補充

### Q6：實際開始／結束日何時計算（與第三階段「無完成核取」）



#### 問題描述

來源 7.1：實際開始＝最早一筆日期工時；實際結束＝**專案標記完成時**最後一筆日期工時。第三階段明確不做完成核取、完成只靠小分類且不寫死名稱。本輪若完全不「標記完成」，實際結束日沒有觸發點。

#### 推薦方案 A：實際開始隨工時自動更新；實際結束要按「標記完成」才寫入，取消完成則清掉實際結束

說明：不寫死任何小分類名稱。專案詳情（專案議題若也要比對實際日，規則相同）多「標記完成／取消完成」。標記完成當下把最後一筆工時日期寫成實際結束；之後再加工時不自動改實際結束，除非再次標記。實際開始永遠等於目前最早工時日。Excel 對應欄空白且網頁已有值 → 不覆蓋＋提醒（對齊 7.2）。


| 面向   | 說明                                |
| ---- | --------------------------------- |
| 推薦原因 | 對齊 7.1 的「完成當下取最後一筆」；又不綁「已完成」小分類名稱 |
| 優點   | 實際結束不會因為持續記工時一直往後跑                |
| 缺點   | 第三階段曾說無完成核取，本輪專案層會多一個完成動作         |
| 開發成本 | **中**。完成狀態＋兩個計算欄＋Excel 空白不覆蓋      |
| 維護成本 | **中**。完成與小分類可能並存，畫面上要寫清楚          |




#### 其他可選方案

**方案 B：不標記完成；實際結束永遠等於目前最後一筆工時日**


| 面向   | 說明                         |
| ---- | -------------------------- |
| 優點   | 不新增完成動作                    |
| 缺點   | 與 7.1 不符；專案未結束時也會一直有「實際結束」 |
| 開發成本 | **低**                      |
| 維護成本 | **中**。語意容易誤解               |


**方案 C：本輪不算實際起迄，只做工時列比對**


| 面向   | 說明            |
| ---- | ------------- |
| 優點   | 避開與第三階段完成規則衝突 |
| 缺點   | 第七章幾乎不做       |
| 開發成本 | **低**         |
| 維護成本 | **中**。下輪還要補   |




#### 建議選擇

> 建議選擇 **A**。

原因：第七章的價值在「完成後鎖實際結束、Excel 空白不覆蓋」。用獨立「標記完成」比猜小分類名稱安全。

#### 使用者選擇

### Q7：Excel 的預計開始／完成如何寫回專案與專案議題



#### 問題描述

第三階段已有預計開始／完成。匯入時 Excel 可能有值、空白、或與網頁不同。來源第七章強調的是**實際**日空白不覆蓋；預計日沒有同樣寫死，需要勾選。

#### 推薦方案 A：Excel 有值才更新預計日；空白不覆蓋網頁；兩邊都有但不同則更新為 Excel 並在結果列出「預計日已改為來源值」

說明：以本次匯入的 Excel 為預計日來源（有值時）。不把空白當成刪除。


| 面向   | 說明                       |
| ---- | ------------------------ |
| 推薦原因 | 匯入目的就是把檔裡的計畫日帶進來；空白不砍手填日 |
| 優點   | 規則單純                     |
| 缺點   | 手改的預計日會被下次有值的 Excel 蓋掉   |
| 開發成本 | **低**                    |
| 維護成本 | **低**                    |




#### 其他可選方案

**方案 B：從不覆蓋預計日，只在不同時列異常**


| 面向   | 說明                |
| ---- | ----------------- |
| 優點   | 保護手改              |
| 缺點   | 匯入幾乎改不到計畫日，要自己改畫面 |
| 開發成本 | **低**             |
| 維護成本 | **低**             |


**方案 C：含空白也覆蓋（空白＝清掉網頁預計日）**


| 面向   | 說明      |
| ---- | ------- |
| 優點   | 與檔完全一致  |
| 缺點   | 容易清掉已填日 |
| 開發成本 | **低**   |
| 維護成本 | **中**   |




#### 建議選擇

> 建議選擇 **A**。

原因：有值才更新、空白不覆蓋，和 7.2「空白不蓋實際日」同一精神，又讓匯入真的帶得進計畫日。

#### 使用者選擇

☑ A — 有值才更新預計日，空白不覆蓋（推薦）

□ B — 預計日只比對不寫回

□ C — 空白也覆蓋（可清空）

### Q8：缺工作表、工作項目沒資料時是否整批停止



#### 問題描述

來源第六章：兩張表都必須**存在**；議題單可以沒列；未寫「工作項目零列」是否等於錯誤。缺表時「停止匯入」已寫明。

#### 推薦方案 A：缺任一必要工作表 → 整批不寫入；工作項目零列也視為錯誤停止；議題單零列允許並繼續（只更新專案側）

說明：與來源「議題單空不是錯、缺表才停」一致，並把「工作項目必須包含專案工作項目」解讀成至少一列可解析資料。


| 面向   | 說明             |
| ---- | -------------- |
| 推薦原因 | 直接採用第六章，少猜測    |
| 優點   | 失敗時資料庫不變，好測    |
| 缺點   | 檔少一張表就要整份重傳    |
| 開發成本 | **低**。先驗工作表再寫入 |
| 維護成本 | **低**          |




#### 其他可選方案

**方案 B：缺議題單仍可只匯工作項目（警告，不當失敗）**


| 面向   | 說明               |
| ---- | ---------------- |
| 優點   | 較寬鬆              |
| 缺點   | 與「議題單必須存在」原文不符   |
| 開發成本 | **低**            |
| 維護成本 | **中**。之後若要變嚴要改契約 |


**方案 C：部分列成功、部分列失敗仍提交成功列**


| 面向   | 說明                  |
| ---- | ------------------- |
| 優點   | 大檔較好救               |
| 缺點   | 半套資料難除錯；與「缺表停止」精神不同 |
| 開發成本 | **中**               |
| 維護成本 | **高**               |




#### 建議選擇

> 建議選擇 **A**。

原因：缺表整批停最接近原文；議題單空繼續，工作項目空則停。

#### 使用者選擇

☑ A — 缺表或工作項目零列整批停；議題單空可繼續（推薦）

### Q9：工時／日期異常要出現在哪裡



#### 問題描述

來源：詳情頁顯眼提醒（實際日 Excel 空白）；匯入結果列出異常；每筆可跳轉專案或專案議題位置。第三階段點專案議題已是 `/projects/{id}?item=`。

#### 推薦方案 A：每次匯入有結果頁（成功摘要＋異常列表＋跳轉）；專案詳情對「Excel 尚未填實際日」另顯示橫幅，直到下次匯入該欄有值或使用者略過

說明：工時四種異常（網頁有／Excel 有／同日不同／無法解析）都在結果頁。跳轉沿用第三階段專案詳情與 `?item=`。橫幅只服務 7.2 實際日缺口，避免詳情被所有工時差塞滿。


| 面向   | 說明                           |
| ---- | ---------------------------- |
| 推薦原因 | 第八章跳轉＋第七章詳情提醒都覆蓋，又不把詳情變成異常清單 |
| 優點   | 匯入當下看得完；日常看專案只留實際日缺口         |
| 缺點   | 要多一個結果畫面                     |
| 開發成本 | **中**。結果頁＋跳轉＋一種橫幅            |
| 維護成本 | **中**                        |




#### 其他可選方案

**方案 B：只有匯入結果頁，詳情不提醒**


| 面向   | 說明                           |
| ---- | ---------------------------- |
| 優點   | 較少常駐 UI                      |
| 缺點   | 關結果頁後 7.2 提醒消失，與來源「詳情顯眼提醒」不符 |
| 開發成本 | **低**                        |
| 維護成本 | **低**                        |


**方案 C：詳情列出該專案全部未解消工時異常，結果頁可省略**


| 面向   | 說明             |
| ---- | -------------- |
| 優點   | 隨時看得到          |
| 缺點   | 詳情變吵；匯入當下少一份總覽 |
| 開發成本 | **中**          |
| 維護成本 | **中**          |

> 建議選擇 **A**。

### Q10：備註工時格式與無法解析時



#### 問題描述

來源舉例：`6/12 - 3H`、`6/15 - 2.5H`。未寫是否允許多行、是否允許 `2026/6/12`、全形、小寫 h。無法解析要提醒（8.1）。

#### 推薦方案 A：一列備註可多行；每行 `M/D - 數字H`（年可省略，省略則用匯入當日的年，若該月日已過完且比今天晚超過合理範圍則用去年——過複雜則改：省略年時用**預計開始年或匯入年，討論時建議固定用檔案匯入當下的西元年**）；小時允許小數；無法解析的行列入異常，不寫入該行，其餘行照寫

說明：建議**省略年＝匯入當天的西元年**（規則單一）。分隔符允許 `-`；`H`／`h` 皆可。其他格式進異常，不擋整份檔（檔仍可匯入其他列／其他行）。


| 面向   | 說明                  |
| ---- | ------------------- |
| 推薦原因 | 對齊舉例；單行壞掉不應整份失敗     |
| 優點   | 可實作、可測              |
| 缺點   | 跨年專案若備註沒年，可能分到錯年    |
| 開發成本 | **中**。解析器＋列異常       |
| 維護成本 | **中**。之後若要支援更多格式再放寬 |




#### 其他可選方案

**方案 B：必須含西元年** `YYYY/M/D - 數字H`**，否則該行異常**


| 面向   | 說明                                |
| ---- | --------------------------------- |
| 優點   | 無跨年歧義                             |
| 缺點   | 與來源舉例 `6/12 - 3H` 不完全相同，既有檔可能大量異常 |
| 開發成本 | **低**                             |
| 維護成本 | **低**                             |


**方案 C：無法解析則整份匯入失敗**


| 面向   | 說明           |
| ---- | ------------ |
| 優點   | 強迫檔案乾淨       |
| 缺點   | 一行錯就全部重來，體感差 |
| 開發成本 | **低**        |
| 維護成本 | **低**        |




#### 建議選擇

> 建議選擇 **A**（省略年＝匯入當下西元年）。

原因：來源舉例沒有年；個人檔常這樣寫。用匯入年比「猜去年」單純。若你的檔一定有年，可改選 B。

#### 使用者選擇

☑ A — 多行 `M/D - nH`，可沒有年（用匯入年）；壞行只列異常（推薦）

□ B — 必須 `YYYY/M/D - nH`

□ C — 任一無法解析則整份失敗

□ 自行補充
