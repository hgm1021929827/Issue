## 三、待確認項目

### Q1：追蹤 TODO 可掛在哪些工作

#### 問題描述

來源 2.3 的工作類型列出議題、專案、專案議題，跳轉也進這三種詳情。第三階段規格曾把「專案或專案議題的 TODO」列為未來規劃。本輪要不要三種都做？

#### 推薦方案 A：三種都做（正式議題、專案、專案議題）

說明：各詳情頁都有「需要追蹤的 TODO」區塊（與一般 TODO 分開）。專案議題的客戶窗口清單跟所屬專案的廠商。

| 面向 | 說明 |
|------|------|
| 推薦原因 | 對齊 2.3 首頁三種工作類型；少做一種首頁就缺一類 |
| 優點 | 一次接上來源；之後不必再為專案補追蹤 |
| 缺點 | 三個詳情都要加區塊 |
| 開發成本 | **中**。三種承載、同一套欄位與下拉 |
| 維護成本 | **低**。規則一致 |

#### 其他可選方案

**方案 B：本輪只做正式議題；專案／專案議題下一輪**

| 面向 | 說明 |
|------|------|
| 優點 | 畫面少兩處 |
| 缺點 | 首頁 2.3 不完整；與「完成這一個功能」不符 |
| 開發成本 | **低**。只改議題詳情＋首頁 |
| 維護成本 | **中**。很快又要接到專案 |

**方案 C：正式議題＋專案；專案議題不算獨立承載（只掛在專案上）**

| 面向 | 說明 |
|------|------|
| 優點 | 少一種承載 |
| 缺點 | 2.3 明列專案議題；從專案議題跳轉會對不準 |
| 開發成本 | **中** |
| 維護成本 | **中**。語意與來源不一致 |

#### 建議選擇

> 建議選擇 **A**。

原因：來源 2.3 已寫三種工作類型與跳轉；第四階段廠商也已接到這三種路徑。

#### 使用者選擇

☑ A — 正式議題、專案、專案議題都可以掛追蹤 TODO（推薦）

□ B — 本輪只做正式議題

□ C — 正式議題＋專案；專案議題不獨立掛

### Q2：與既有一般 TODO 的關係

#### 問題描述

正式議題已有多層一般 TODO（`issue_todo`）。來源寫「與一般 TODO 分開顯示」，欄位也不一樣（沒有內容／排序／子項，多了追蹤對象）。要不要做成同一棵樹上的標記？

#### 推薦方案 A：獨立清單，不是一般 TODO 的一種

說明：詳情頁兩個區塊。一般 TODO 維持第一階段行為。追蹤 TODO 另列，不出現在一般 TODO 樹，也不能拖進那棵樹。

| 面向 | 說明 |
|------|------|
| 推薦原因 | 對齊來源「分開顯示」與不同欄位；預約 10.4 也不把追蹤列入處理事項 |
| 優點 | 完成規則、拖曳、父子不會互相污染 |
| 缺點 | 同一頁兩套清單 |
| 開發成本 | **中**。新實體與新區塊，不改一般 TODO 契約 |
| 維護成本 | **低**。界線清楚 |

#### 其他可選方案

**方案 B：同一棵樹，用標記區分「一般／追蹤」**

| 面向 | 說明 |
|------|------|
| 優點 | 少一種清單元件 |
| 缺點 | 來源欄位不合；父自動完成、拖曳排序會跟追蹤對象纏在一起 |
| 開發成本 | **高**。要改第一階段 TODO 契約 |
| 維護成本 | **高**。熔斷風險 |

**方案 C：把一般 TODO 加「追蹤對象」選填欄，不再做第二種 TODO**

| 面向 | 說明 |
|------|------|
| 優點 | 表面少一種資料 |
| 缺點 | 違反「分開顯示」；首頁「需要追蹤項目」要從一般 TODO 過濾，語意歪掉 |
| 開發成本 | **中** |
| 維護成本 | **高** |

#### 建議選擇

> 建議選擇 **A**。

原因：來源把兩種 TODO 分開寫；硬合併會動到已結束的第一階段契約。

#### 使用者選擇

☑ A — 獨立清單，與一般 TODO 分開（推薦）

□ B — 同一棵樹加標記

### Q3：追蹤 TODO 要不要多層、排序、父項自動完成

一般 TODO 有子項、拖曳排序、父項自動完成。第二章追蹤 TODO **沒寫**這些。要不要沿用？

#### 推薦方案 A：單層平鋪；不可建子項；不拖曳排序；無父項自動完成

說明：只有勾選完成、改標題、選對象、刪除。列表順序穩定即可（例如建立先後），本輪不提供拖曳改序。

| 面向 | 說明 |
|------|------|
| 推薦原因 | 來源 2.1 沒有內容／順序／子項；追蹤是「誰該回我」，不是拆工 |
| 優點 | 範圍小、不複製第一章規則 |
| 缺點 | 之後若要排序得再做 |
| 開發成本 | **低**。平鋪 CRUD |
| 維護成本 | **低** |

#### 其他可選方案

**方案 B：單層但可拖曳排序（仍無子項、無自動完成）**

| 面向 | 說明 |
|------|------|
| 優點 | 首頁與詳情順序可調 |
| 缺點 | 來源沒要求；多一套排序互動 |
| 開發成本 | **中**。同層拖曳 |
| 維護成本 | **低** |

**方案 C：完全沿用一般 TODO（多層＋拖曳＋父自動完成）再加追蹤對象**

| 面向 | 說明 |
|------|------|
| 優點 | 操作一致 |
| 缺點 | 來源沒寫；與 Q2＝A 的「不同種」衝突；成本高 |
| 開發成本 | **高** |
| 維護成本 | **中** |

#### 建議選擇

> 建議選擇 **A**。

原因：第二章沒有子項與排序；把第一章規則套過來是過度設計。

### Q6：未設廠商、該公司沒有窗口時怎麼提示

#### 問題描述

2.2：工作尚未設定廠商時，選「客戶窗口」須提示先設廠商。第四階段之後**新存**的專案／正式議題廠商已必填，但舊資料仍可能空白；專案議題跟專案，舊專案也可能尚未補廠商。公司有了但還沒建窗口，來源沒寫。

#### 推薦方案 A：保留 2.2 提示；舊資料未設廠商時不可選窗口；該公司無窗口時另提示去成員頁新增，不可存空窗口

說明：選「客戶窗口」時：無廠商 → 提示先到該工作補廠商（專案議題則提示去專案補）。有廠商但窗口清單為空 → 提示先在成員維護新增窗口。有窗口則只列該公司的窗口。選「內部成員」不受廠商影響。

| 面向 | 說明 |
|------|------|
| 推薦原因 | 來源有未設廠商路徑；舊資料仍會走到；無窗口是實際缺口，不提示會存失敗卻看不懂 |
| 優點 | 兩種缺資料都有明確下一步 |
| 缺點 | 多兩句提示文案 |
| 開發成本 | **低**。條件提示，不改廠商必填規則 |
| 維護成本 | **低** |

#### 其他可選方案

**方案 B：認定廠商已必填，拿掉「先設廠商」提示；只處理無窗口**

| 面向 | 說明 |
|------|------|
| 優點 | 少一條分支 |
| 缺點 | 舊資料未補廠商時選客戶窗口會莫名沒選項 |
| 開發成本 | **低** |
| 維護成本 | **中**。舊資料踩雷 |

**方案 C：無廠商或無窗口時，允許改選「全部窗口」（不限該公司）**

| 面向 | 說明 |
|------|------|
| 優點 | 一定選得到人 |
| 缺點 | 違反 2.2「所屬客戶公司的窗口」 |
| 開發成本 | **中** |
| 維護成本 | **高**。之後預約窗口過濾也不一致 |

#### 建議選擇

> 建議選擇 **A**。

原因：2.2 原文仍適用於舊資料；無窗口是使用上一定會碰到的空狀態。

#### 使用者選擇

☑ A — 無廠商提示先設；無窗口提示先新增；不可選別家窗口（推薦）

□ B — 不做未設廠商提示，只處理無窗口

□ C — 缺資料時改列全部窗口

### Q7：改廠商時，已選「客戶窗口」的追蹤 TODO 怎麼辦

#### 問題描述

追蹤對象指向某公司的窗口後，若把該議題／專案的廠商改成別家，舊窗口就不屬於新公司。第四階段改廠商目前沒有這種檢查。

#### 推薦方案 A：有「客戶窗口」類追蹤 TODO 時，不可改廠商；提示筆數，須先改對象或刪那些 TODO

說明：內部成員類追蹤不擋改廠商。專案改廠商時，專案自己與底下專案議題的客戶窗口追蹤都算占用。

| 面向 | 說明 |
|------|------|
| 推薦原因 | 避免畫面還顯示已不屬於該公司的窗口；比默默清空安全 |
| 優點 | 資料不會指到錯公司 |
| 缺點 | 改廠商前多一步清理 |
| 開發成本 | **中**。改廠商前計數 |
| 維護成本 | **低**。規則明確 |

#### 其他可選方案

**方案 B：允許改廠商，那些 TODO 改標「對象失效」，進詳情須重選才能再存該筆**

| 面向 | 說明 |
|------|------|
| 優點 | 不擋改廠商 |
| 缺點 | 來源沒有失效態；首頁可能出現壞掉的對象 |
| 開發成本 | **中**。多一種狀態 |
| 維護成本 | **中** |

**方案 C：允許改廠商，自動清空那些 TODO 的對象（或整筆刪）**

| 面向 | 說明 |
|------|------|
| 優點 | 實作單純 |
| 缺點 |  silently 丟資料；若 Q5＝A 清空後還不能存 |
| 開發成本 | **低** |
| 維護成本 | **高**。使用者不知道追蹤去哪 |

#### 建議選擇

> 建議選擇 **A**。

原因：與刪除占用同一思路——有人在用就先處理引用，不要默默壞掉。

□ B — 可改廠商，對象標失效須重選

□ C — 可改廠商，自動清空或刪那些 TODO

### Q8：刪成員、客戶公司、窗口時要不要檢查追蹤 TODO

#### 問題描述

來源 9.1：刪成員前檢查追蹤 TODO。9.2：刪公司／窗口前檢查議題、專案、追蹤 TODO、預約。第四階段 MF-F08 當時「不檢查尚未存在的追蹤 TODO」；窗口目前沒有工作指向，刪窗口不擋。本輪有實體後要不要補上？

| 面向 | 說明 |
|------|------|
| 推薦原因 | 對齊第九章；否則刪窗口會讓追蹤對象消失 |
| 優點 | 與第四階段占用提示同一種體驗 |

| 維護成本 | **低**。延續 MF-F08 |

| 面向 | 說明 |
|------|------|
| 優點 | 窗口較好清 |
| 缺點 | 刪窗口會 silently 少追蹤；與 9.2 不符 |
| 開發成本 | **中** |
| 維護成本 | **中** |

**方案 C：本輪不擴大刪除檢查（維持第四階段）**

| 面向 | 說明 |
|------|------|
| 優點 | 少改成員頁 |
| 缺點 | 違反第九章；刪窗口後追蹤壞掉 |
| 開發成本 | **低** |
| 維護成本 | **高** |

> 建議選擇 **A**。

原因：來源已寫刪前檢查追蹤；第四階段只是當時沒實體才暫不查。

### Q10：跳轉落點

#### 問題描述

2.3：點跳轉進入對應的議題、專案或專案議題詳情頁。要不要捲到該筆追蹤 TODO？

#### 推薦方案 A：進入詳情並盡力捲動／標示該筆追蹤 TODO；找不到該筆仍打開詳情並提示

說明：所屬工作顯示：議題用標題（可附編號）；專案用代號＋名稱；專案議題用項次＋標題。工作類型文案固定「議題／專案／專案議題」。定位互動待 Tech Spike；若深頁捲動不可靠，至少打開詳情且追蹤區塊可見。

| 面向 | 說明 |
|------|------|
| 推薦原因 | 「跳轉」若只開詳情、人還要自己找，追蹤列表價值減半 |
| 優點 | 從首頁一鍵對到那筆 |
| 缺點 | 捲動／高亮要 Spike |
| 開發成本 | **中**。含 Spike |
| 維護成本 | **低** |

#### 其他可選方案

**方案 B：只打開詳情頁，不定位到該筆**

| 面向 | 說明 |
|------|------|
| 優點 | 實作單純、對齊 2.3 字面「進入詳情頁」 |
| 缺點 | 追蹤多筆時要自己找 |
| 開發成本 | **低** |
| 維護成本 | **低** |

**方案 C：首頁可直接勾完成，跳轉只是次要**

| 面向 | 說明 |
|------|------|
| 優點 | 少進詳情 |
| 缺點 | 來源首頁欄位沒有完成核取；詳情才是編輯處 |
| 開發成本 | **中** |
| 維護成本 | **中**。兩處都能完成，狀態要同步 |

> 建議選擇 **A**。

原因：首頁已有跳轉按鈕，落點應對準那筆；做不到精準捲動時仍須打開正確詳情（Spike 可降級為 B 的行為）。
