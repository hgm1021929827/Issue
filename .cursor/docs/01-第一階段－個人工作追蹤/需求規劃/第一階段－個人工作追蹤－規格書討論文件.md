## 三、待確認項目



### Q1：本輪 MVP 切分



#### 問題描述

完整系統包含議題、專案、Excel、加簽、成員、預約連線等。一次做完開發與驗收風險高。是否把第一階段收斂成可交付的核心，其餘開下一階段？

#### 推薦方案 A：分三輪；第一階段只做核心追蹤

**第一階段 Must：** 單人使用；分類設定（四個固定大分類＋小分類規則）；正式議題 CRUD 與詳情；一般 TODO＋子 TODO＋父自動完成；首頁工作清單。  
**下一階段：** 專案／專案議題、Excel 匯入與工時／日期比對、臨時工作。  
**再下一階段：** 成員與客戶窗口、需要追蹤的 TODO、加簽恢復、預約連線與行事曆。


| 面向   | 說明                                     |
| ---- | -------------------------------------- |
| 推薦原因 | 核心路徑可先上手；專案匯入與預約依賴成員／廠商資料，適合後做         |
| 優點   | 範圍清楚；QA 可驗收；後續階段不覆寫本階段正式文件             |
| 缺點   | 來源檔一次寫到的功能，不會在第一階段全部出現                 |
| 開發成本 | **中**。第一階段不含 Excel／預約，但仍有分類＋議題＋巢狀 TODO |
| 維護成本 | **低**。之後增量開新階段即可                       |




#### 其他可選方案

**方案 B：第一階段一次做完整系統（來源檔全部＋反推既有）**


| 面向   | 說明                            |
| ---- | ----------------------------- |
| 優點   | 一次對齊來源檔全文                     |
| 缺點   | 規格、資料模型、匯入與預約同時開展，易拖長且難驗收     |
| 開發成本 | **高**。Excel 解析、工時比對、預約行事曆皆在本輪 |
| 維護成本 | **高**。未驗證的核心規則與週邊功能綁在一起       |


**方案 C：第一階段做核心＋專案（不含 Excel、預約、成員）**


| 面向   | 說明                        |
| ---- | ------------------------- |
| 優點   | 議題與專案可一起看                 |
| 缺點   | 專案主資料、工時欄位仍缺來源檔細節，本輪假設會變多 |
| 開發成本 | **中**。比 A 多專案 CRUD，仍避開匯入  |
| 維護成本 | **中**                     |




#### 建議選擇

> 建議選擇 **A**。

原因：先讓「分類 → 議題 → TODO／子 TODO → 首頁」可日常使用；來源檔其餘章節保留為後續階段 Must，不刪除產品願景。

#### 使用者選擇

☑ A — 分三輪，第一階段只做核心（推薦）

□ B — 第一階段一次做完整

□ C — 第一階段核心＋專案，不含 Excel／預約／成員

### Q3：使用對象與登入



#### 問題描述

專案定位是個人 Web，但來源檔有「公司成員、客戶窗口、追蹤對象」。這些人是**資料**（你記錄誰該追），還是會**登入操作**的帳號？

#### 推薦方案 A：單人使用；成員與客戶只當資料；本輪不做登入帳號

說明：只有你在瀏覽器使用。內部成員、客戶公司、窗口是通訊錄與下拉選項，沒有各自密碼。本輪不實作登入頁（本機直接進系統）。若以後要擋外人，再開階段加簡單保護。


| 面向   | 說明                             |
| ---- | ------------------------------ |
| 推薦原因 | 對齊「個人 Web」；來源檔的成員維護是通訊錄，不是權限系統 |
| 優點   | 無帳號流程；開發快                      |
| 缺點   | 本機未設防；無法多人同時分帳使用               |
| 開發成本 | **低**。不做認證                     |
| 維護成本 | **低**                          |




#### 其他可選方案

**方案 B：單人使用，但要本機登入（一組帳密）**


| 面向   | 說明                             |
| ---- | ------------------------------ |
| 優點   | 略擋無關的人開瀏覽器                     |
| 缺點   | 要做登入頁、工作階段、忘記密碼策略（個人系統常變成寫死帳密） |
| 開發成本 | **中**。認證與前端路由守衛                |
| 維護成本 | **中**                          |


**方案 C：多使用者登入，成員即帳號，有權限差異**


| 面向   | 說明                   |

| 優點   | 可給同事用                |
| 缺點   | 超出個人系統；權限、資料隔離來源檔未定義 |
| 開發成本 | **高**。帳號、角色、授權       |
| 維護成本 | **高**                |

> 建議選擇 **A**。

原因：成員／窗口在來源檔是追蹤與預約的資料來源，不是登入主體。第一階段更不該先做帳號系統。

#### 使用者選擇

### Q5：議題「完成」怎麼表示



#### 問題描述

TODO 有「是否完成」核取。議題有大分類「已完成」。兩者若同時存在，會出現「核取完成但分類還在處理中」的矛盾。

#### 推薦方案 A：議題完成＝把大分類改為「已完成」；沒有獨立的議題完成核取


| 面向   | 說明                       |
| ---- | ------------------------ |
| 推薦原因 | 四個大分類已包含「已完成」；與來源檔分類模型一致 |
| 優點   | 單一真相；畫面顏色跟分類             |
| 缺點   | 不能「完成但仍留在處理中」            |
| 開發成本 | **低**                    |
| 維護成本 | **低**                    |




#### 其他可選方案

**方案 B：議題另有完成核取；改核取時自動把大分類改為已完成／處理中**


| 面向   | 說明                           |
| ---- | ---------------------------- |
| 優點   | 操作像 TODO                     |

| 開發成本 | **中**                        |

| 開發成本 | **低**      |

原因：避免雙狀態；TODO 才用核取，議題用分類。

### Q6：子 TODO 層級與排序範圍



#### 問題描述

來源檔：父 TODO 下可有多筆子 TODO，欄位相同，可拖曳排序。未寫子 TODO 底下能否再有子項，也未寫能否拖到別的父項底下。

#### 推薦方案 A：僅一層子 TODO；拖曳只改同一層的排列順序，不可拖去其他父項

說明：父項之間排序、同一父項下子項排序，兩套順序。要改掛父項用編輯／移動動作（若本輪不做移動，就刪除後重建）。父自動完成規則維持來源檔：只在勾選「最後一筆未完成子 TODO」時把父標完成；取消子項不自動取消父；手動改父不改子。


| 面向   | 說明                             |
| ---- | ------------------------------ |
| 推薦原因 | 來源檔的自動完成只描述一層；多層會讓「最後一筆未完成」難定義 |
| 優點   | 規則清楚；拖曳實作單純                    |
| 缺點   | 不能做三層清單；改掛父項較麻煩                |
| 開發成本 | **中**。巢狀 CRUD＋兩層拖曳             |
| 維護成本 | **低**                          |




#### 其他可選方案

**方案 B：僅一層，但允許把子 TODO 拖到另一個父 TODO 底下**


| 面向   | 說明                |
| ---- | ----------------- |
| 優點   | 整理清單較快            |
| 缺點   | 拖曳要處理跨父、順序重算；誤拖風險 |
| 開發成本 | **中**             |
| 維護成本 | **中**             |


**方案 C：允許多層（孫 TODO）**


| 面向   | 說明                      |
| ---- | ----------------------- |
| 優點   | 可拆很細                    |
| 缺點   | 自動完成、拖曳、畫面都明顯變複雜；來源檔未要求 |
| 開發成本 | **高**                   |
| 維護成本 | **高**                   |




#### 建議選擇

> 建議選擇 **A**。

原因：對齊來源檔第一章的自動完成敘述，避免尚未定義的多層規則。

#### 使用者選擇

□ A — 僅一層；拖曳不改掛父項（推薦）

□ B — 僅一層；可拖到其他父項

☑ C — 允許多層

□ 自行補充

### Q7：沒有子 TODO 的父項如何完成



#### 問題描述

來源檔的父自動完成只在「有子項且最後一筆未完成被勾選」時觸發。沒有子項時，父項要怎麼標完成？

#### 推薦方案 A：無子項時，父 TODO 用自己的「是否完成」核取，與一般 TODO 相同


| 面向   | 說明                                              |
| ---- | ----------------------------------------------- |
| 推薦原因 | 尚未拆子項的工作仍要能勾完                                   |
| 優點   | 與「一般 TODO 欄位含是否完成」一致                            |
| 缺點   | 有子項時畫面同時有父核取與子核取，需避免誤解（父仍可手動改，且不連動子項——來源檔已如此規定） |
| 開發成本 | **低**                                           |
| 維護成本 | **低**                                           |




#### 其他可選方案

**方案 B：一旦新增任一子項，隱藏父核取，只靠自動完成與手動例外**


| 面向   | 說明                           |
| ---- | ---------------------------- |
| 優點   | 有子項時較不易誤勾父項                  |
| 缺點   | 來源檔允許手動取消已自動完成的父項，隱藏核取後這步較難找 |
| 開發成本 | **中**。狀態切換 UI                |

**方案 C：無子項不可標完成，必須先加子項**

### Q8：大分類是否固定四種、顏色誰決定



#### 問題描述

來源檔：固定大分類由三種加為四種（已完成、處理中、加簽中、預約），顏色不同；「預約」的小分類由使用者維護，並給初始範例。未寫大分類能否自行增刪，也未寫顏色是系統寫死還是可改。

#### 推薦方案 A：四個大分類系統固定，不可增刪改名；顏色系統寫死；小分類由使用者維護（預約給初始範例）

說明：空白小分類不建資料、以空值表示；畫面顯示大分類名稱與大分類顏色（來源檔 4.2）。同一大分類下小分類名稱不可重複；不同大分類可同名。刪前檢查使用中資料（正式議題、臨時工作、專案、專案議題、加簽前原小分類、預約連線）。


| 面向   | 說明                                  |
| ---- | ----------------------------------- |
| 推薦原因 | 來源檔稱「固定大分類」；預約主要供預約狀態，不宜讓使用者再造第五個大類 |
| 優點   | 狀態語意穩定；SA／RD 好做篩選與顏色                |
| 缺點   | 不能自己加「暫停」這類第五大類                     |
| 開發成本 | **低**。大分類種子資料＋小分類 CRUD              |
| 維護成本 | **低**                               |




#### 其他可選方案

**方案 B：四個大分類固定，但顏色可在分類設定頁修改**


| 面向   | 說明             |
| ---- | -------------- |
| 優點   | 可依個人習慣配色       |
| 缺點   | 要存顏色值、預設與對比可讀性 |
| 開發成本 | **中**          |
| 維護成本 | **中**          |


**方案 C：大分類也可由使用者增刪**


| 面向   | 說明                 |
| ---- | ------------------ |
| 優點   | 最彈性                |
| 缺點   | 「加簽／預約」特殊流程會失去固定錨點 |
| 開發成本 | **高**              |
| 維護成本 | **高**              |




#### 建議選擇

> 建議選擇 **A**。

原因：對齊「固定大分類」與預約狀態用途；小分類留給你日常細分。

### Q9：第一階段首頁要有什麼



#### 問題描述

| 面向   | 說明                             |

| 開發成本 | **低**                          |

### Q10：臨時工作、加簽在第一階段怎麼處理



#### 問題描述

若 Q1 選 A，臨時工作與加簽完整流程都不在本輪，但分類已有「加簽中」。使用者仍可能把議題大分類改成「加簽中」。要不要在本輪提供「進入加簽／回到手上並恢復小分類 ID」？

#### 推薦方案 A：本輪可手動把10議題改到任一固定大分類（含加簽中、預約）；不做加簽保存／恢復、不做臨時工作類型

說明：小分類仍用 ID 存，刪除規則若本輪只有正式議題，就只檢查正式議題。加簽保存原大小分類、恢復或改為「處理中＋空白小分類」，以及臨時工作，寫入後續階段，不當作已實作。


| 面向   | 說明                                      |
| ---- | --------------------------------------- |
| 推薦原因 | 分類資料模型先正確（ID、空白選項、同名不同 ID）；流程功能等有議題主體再做 |
| 優點   | 本輪規則少；與來源檔第三章不假裝已完成                     |
| 缺點   | 本輪選「加簽中」只是換分類，沒有真正加簽                    |
| 開發成本 | **低**                                   |
| 維護成本 | **低**。後續階段補流程                           |




#### 其他可選方案

**方案 B：本輪實作加簽保存與依小分類 ID 恢復；臨時工作仍延後**

| 優點   | 來源檔 3.2 提早落地                   |
| 缺點   | 「進入加簽」的操作入口來源檔沒寫（誰按、能否從加簽中再改走） |
| 開發成本 | **中**                          |
| 維護成本 | **中**                          |

| 面向   | 說明                   |
| ---- | -------------------- |
| 優點   | 刪除小分類的檢查對象較齊         |

原因：加簽與臨時工作缺少流程與欄位定義；本輪只保證分類與議題資料能存對 ID，避免假實作。
