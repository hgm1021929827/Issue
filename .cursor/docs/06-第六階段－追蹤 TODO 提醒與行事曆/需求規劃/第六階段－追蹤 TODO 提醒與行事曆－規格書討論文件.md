## 三、待確認項目

### Q1：哪些追蹤 TODO 可以填提醒日期

#### 問題描述

第五階段三種工作都能掛追蹤。提醒要三種都有，還是先做正式議題？

#### 推薦方案 A：三種都有（議題、專案、專案議題上的追蹤 TODO）

說明：同一套欄位。行事曆點擊沿用第五階段跳轉（含專案議題 `?item=`＋`trackTodo=`）。

| 面向 | 說明 |
|------|------|
| 推薦原因 | 追蹤實體只有一種；只做議題會讓專案上的追蹤無法進月曆 |
| 優點 | 規則一致、一次做完 |
| 缺點 | 月曆來源再多一種，三種跳轉都要測 |
| 開發成本 | **低**。同一欄、同一查詢，差在跳轉已有 |
| 維護成本 | **低** |

#### 其他可選方案

**方案 B：本輪只做掛在正式議題上的追蹤**

| 面向 | 說明 |
|------|------|
| 優點 | 月曆跳轉只走議題路徑 |
| 缺點 | 專案／專案議題的追蹤沒提醒；之後還要再做一輪 |
| 開發成本 | **低**。少兩種跳轉測試 |
| 維護成本 | **中**。兩套規則 |

#### 建議選擇

> 建議選擇 A。

原因：提醒是追蹤 TODO 的屬性，不該依所屬工作切開。

### Q4：一筆追蹤幾個提醒日

#### 問題描述

正式議題的「預計項目」可多天。提醒要不要也多天？

#### 推薦方案 A：一筆追蹤最多一個提醒日

說明：改日期＝改那一天在月曆上的位置。不是拖曳排程。

| 面向 | 說明 |
|------|------|
| 推薦原因 | 「多一個提醒日期」是單欄；與預計項目分責（預計項目＝議題要做哪幾天，提醒＝這筆追蹤要跟誰的那天） |
| 優點 | 規則簡單、不會和議題拖曳搶語意 |
| 缺點 | 同一筆追蹤不能佔好多天 |
| 開發成本 | **低**。單一可空日期 |
| 維護成本 | **低** |

#### 其他可選方案

**方案 B：一筆可多個提醒日（類似預計項目）**

| 面向 | 說明 |
|------|------|
| 優點 | 連續幾天要跟同一件事 |
| 缺點 | 等於再做一套排程；容易和議題預計項目搞混 |
| 開發成本 | **高**。多列、增刪、與月曆雙向 |
| 維護成本 | **高** |

#### 建議選擇

> 建議選擇 A。

原因：本輪只要「日期欄同步到月曆」，不要複製預計項目。

### Q6：月曆上要獨立視角，還是併進「到期日」

#### 問題描述

現在切換「到期日／預計項目」。追蹤提醒要第三顆開關，還是跟到期日混在一起？

#### 推薦方案 A：第三個視角開關「追蹤提醒」，預設開啟

說明：可只看到期、只看預計項目、只看追蹤，或任意組合。標記點擊進對應工作並定位該筆追蹤。

| 面向 | 說明 |
|------|------|
| 推薦原因 | 三種資料語意不同；混進到期日會讓「議題哪天要交」和「哪天要跟人」分不清 |
| 優點 | 可關追蹤以免格子太滿 |
| 缺點 | 頂部多一顆開關 |
| 開發成本 | **中**。現有前端把非 plan 都當 due，要拆第三種 |
| 維護成本 | **低**。開關語意清楚 |

#### 其他可選方案

**方案 B：併入「到期日」視角，不另開開關**

| 面向 | 說明 |
|------|------|
| 優點 | UI 少一顆 |
| 缺點 | 關到期日會連追蹤提醒一起消失；圖示要很清楚才能分辨 |
| 開發成本 | **低**。當 due 丟進去即可 |
| 維護成本 | **中**。使用者可能抱怨找不到開關 |

#### 建議選擇

> 建議選擇 A。

原因：這正是 Spike 要解的 `kind` 二分；獨立開關比混在到期日安全。

## 四、本輪預設不做（已拒絕方向，待你確認後寫入正式規格第十一章）

| 項目 | 原因 |
|------|------|
| 從月曆拖曳來「設定」提醒日 | 與議題預計項目拖曳衝突；本輪只要表單日期→月曆 |
| 在月曆上點一下就刪除提醒 | 預計項目可以點掉；提醒建議回詳情改日期，避免誤刪追蹤本身 |
| 瀏覽器／郵件通知 | 無登入、無通知基礎設施 |
| 匯出 ICS／Google 日曆 | 超出「同步到本系統行事曆」 |
