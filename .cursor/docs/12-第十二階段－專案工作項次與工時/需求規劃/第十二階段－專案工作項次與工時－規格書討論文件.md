## 一、討論前提

下列前提若不同意，請在對應題目選「自行補充」：

- 本系統仍為**個人使用**；使用者可見文案繁體中文。
- **已確認、本輪不得改成登入系統：** 第一階段 Q3＝A。成員與客戶是通訊錄，沒有各自帳密。
- **本階段做：** 專案工作項次、工時、專案 Excel（只讀「工作項目」「議題單」）、再次匯入差異、備註工時比對。
- **本階段不做、不在本文件當「要不要做」勾選：** 正式議題匯入（`議題匯入範本.xls`）、專案檔其他工作表、加簽恢復、預約連線、臨時工作、登入。
- **不改**第一～十一階段正式文件本文。本輪用增量接上。
- 補充文件與舊第四階段 Excel 原稿衝突時，**以補充文件為準**。舊稿與 Template 只當對照。
- 補充文件已定、**本文件不再當「要不要做」勾選**（實作細節交 SA）：
  - 工作項次與專案議題平行隸屬專案，互不從屬
  - 工作項次唯一識別＝專案編號＋工作代號；專案議題＝專案編號＋項次
  - 工作代號即使寫成 `3.1.1`，系統不推導父子、階層或排序
  - 工時只掛工作項次或專案議題；同日最多一筆；不算專案總工時
  - 實際開始＝該筆最早工時日；實際結束＝標記完成時取最後一筆工時日
  - Excel 備註工時只逐日比對，不自動新增／修改／刪除網頁工時；網頁工時備註不與 Excel 備註文字比對
  - 工作項次管理欄位（工作代號、工作說明、計畫人天、負責人員、預計開始日、預計完成日）網頁不可手改；再次匯入直接更新
  - 本次未找到不得自動刪；使用者選保留（明顯標示）或刪除；日後重新出現則取消標示
  - 唯一識別變更＝舊未找到＋新新增
- 角色提示中的 `category` 僅為格式示範。API／套件屬 SA／Tech Spike，不在本文件勾選。

待 Tech Spike 評估：ClosedXML 讀 `.xlsx`（含 Excel 日期序號）；備註工時多種寫法容錯；匯入結果頁保留／刪除；未找到標示與專案頁並陳是否擁擠。

### Q1：無登入時，「目前使用者」怎麼指定

#### 問題描述

補充 §3.1／§4.1：匯入依負責人員／處理人篩選「目前使用者」。系統沒有登入，無法知道你是誰。

#### 推薦方案 A：每次匯入時下拉選一位公司成員，當作本次「目前使用者」

說明：用第四階段成員主檔。篩選比對 Excel 負責人員／處理人與該成員中文名（去空白、忽略大小寫）。不持久化成登入身分。

| 面向 | 說明 |
|------|------|
| 推薦原因 | 不開登入就能對齊補充「目前使用者」；成員主檔已有 |
| 優點 | 可切換成同事視角重匯；規則清楚 |
| 缺點 | 每次要選人 |
| 開發成本 | **低**。一個下拉加字串比對 |
| 維護成本 | **低** |

#### 其他可選方案

**方案 B：匯入時手填姓名字串，不綁成員主檔**

| 面向 | 說明 |
|------|------|
| 優點 | 不必先建成員 |
| 缺點 | 與第四階段主檔脫鉤；拼字易漏篩 |
| 開發成本 | **低**。一個文字欄 |
| 維護成本 | **中**。兩套姓名來源 |

**方案 C：不過濾，整張表有效列都匯入**

| 面向 | 說明 |
|------|------|
| 優點 | 實作最短 |
| 缺點 | 違反補充「只匯與目前使用者相關」 |
| 開發成本 | **低** |
| 維護成本 | **高**。之後難補篩選語意 |

#### 建議選擇

> 建議選擇 **A**。

原因：維持單人無登入，又能用既有成員清單表達「這次我是誰」。

#### 使用者選擇

☑ A — 匯入時下拉選公司成員當目前使用者（推薦）；匯入頁記住上次選的人

□ B — 匯入時手填姓名

□ C — 不過濾，整表匯入

□ 自行補充

補充確認：大多是固定人，故下拉預設上次選擇，仍可改。

### Q7：負責人員／處理人篩選怎麼比對

實檔負責人員可為「蕭維德、李中凱」、含客戶名、或 `All`。補充只說依負責人員／處理人篩目前使用者。

#### 推薦方案 A：儲存格文字包含目前使用者中文名即通過；`All`（忽略大小寫）視為通過

說明：用「包含」不是整格全等。逗號、頓號、換行都當成分隔後再比，或直接對整格做包含比對即可（SA 定正規化）。處理人欄同樣規則。

| 面向 | 說明 |
|------|------|

| 缺點 | 短名可能誤中（例如「李」）— 實務用完整中文名可接受 |
| 開發成本 | **低**。字串正規化 |
| 維護成本 | **低** |

#### 其他可選方案

**方案 B：整格去空白後必須與中文名全等**

### Q9：未找到的保留／刪除何時決定

#### 問題描述

補充 §8：未找到不得自動刪，使用者選保留（明顯標示）或刪除。沒寫是匯入當下決定，還是之後在詳情慢慢處理。

#### 推薦方案 A：匯入結果頁一次列出未找到列，每筆選保留或刪除後才結束這次匯入

說明：管理欄位更新與新增在同一交易先寫入；未找到的刪除等你在結果頁確認。重新整理結果頁若沒有暫存，應提示「請重匯」（Spike 定是否暫存）。

| 面向 | 說明 |
|------|------|
| 推薦原因 | 差異處理與「這次匯入」綁在一起，不會忘 |
| 優點 | 一次看完 |
| 缺點 | 未找到很多時結果頁會長 |
| 開發成本 | **中**。結果頁要可操作，不是純報告 |
| 維護成本 | **中** |

#### 其他可選方案

**方案 B：匯入先全部標成「未找到／待處理」；之後在專案詳情逐筆保留或刪除**

| 面向 | 說明 |
|------|------|
| 優點 | 匯入當下較快 |
| 缺點 | 容易一直待處理；與「本次匯入」脫鉤 |
| 開發成本 | **中** |
| 維護成本 | **中** |

**方案 C：未找到一律自動保留並標示，不在匯入流程問刪除（刪除改走一般刪除）**

| 面向 | 說明 |
|------|------|
| 優點 | 結果頁只讀 |
| 缺點 | 補充明列匯入時可選刪除；一般刪除與「有工時仍允許刪」要另開入口 |
| 開發成本 | **低** |
| 維護成本 | **中** |

#### 建議選擇

> 建議選擇 **A**。

原因：補充把保留／刪除寫在「本次匯入」差異裡，結果頁一次做完最不容易漏。

#### 使用者選擇

### Q10：議題單要匯哪些欄、網頁哪些不可改

#### 問題描述

補充 §7.1 只鎖定**工作項次**管理欄位。專案議題第三階段已可手改標題、內容、分類、日期。議題單實檔欄很多（提報人、類型、UAT、版號等）。

#### 推薦方案 A：議題單只匯項次、需求說明→標題、解決方案→內容、處理人員、預計完成日、備註（比對工時）；項次網頁不可改；其餘已存在欄位維持可手改，再匯入時有對到的欄就更新

說明：不為 UAT／版號／提報人另做實體。處理人員本輪存文字即可（不是成員 FK）。項次是唯一識別，鎖定。

| 面向 | 說明 |
|------|------|
| 推薦原因 | 對齊補充「議題單＝專案議題」又不炸掉第三階段手維護 |
| 優點 | 範圍可控；項次不會被手改到對不到 Excel |
| 缺點 | 實檔很多欄用不到 |
| 開發成本 | **中**。對既有議題加處理人文字與工時 |
| 維護成本 | **低** |

#### 其他可選方案

**方案 B：議題單欄位比照工作項次，能對到的都鎖定、只能靠再匯入改**

| 面向 | 說明 |
|------|------|
| 優點 | 兩種資料規則對稱 |
| 缺點 | 第三階段已能手改議題，會變成「匯入後就不能改標題」 |
| 開發成本 | **中** |
| 維護成本 | **中**。與既有操作衝突 |

**方案 C：議題單本輪不匯入，只匯工作項目；議題維持手維護**

| 面向 | 說明 |
|------|------|
| 優點 | 範圍小 |
| 缺點 | 違反本階段已凍結的「讀議題單」與補充 §4 |
| 開發成本 | **低** |
| 維護成本 | **高**。很快要補 |

#### 建議選擇

> 建議選擇 **A**。

原因：鎖定識別（項次），其餘沿用已能手改的專案議題；UAT 等欄不進系統。

#### 使用者選擇

☑ A — 匯核心欄；項次鎖定；其他可手改、再匯入更新（推薦）

□ B — 議題對到的欄全部鎖定，只能靠 Excel 改

□ C — 本輪不匯議題單

### Q12：標記完成放哪、無工時能不能完成

#### 問題描述

補充 §5.6：實際結束只在「標記完成」時取最後一筆工時日。沒寫按鈕在哪、沒有工時時能不能完成。

#### 推薦方案 A：工作項次與專案議題詳情各有「標記完成／取消完成」；無工時不可標記，提示先有工時

說明：完成不是改分類。取消完成清空實際結束，不刪工時。再加工時不自動改實際結束（對齊舊稿精神，補充未反駁）。

| 面向 | 說明 |
|------|------|
| 推薦原因 | 補充明寫標記完成才有實際結束；無工時沒有「最後一筆」 |
| 優點 | 實際日一定算得出來 |
| 缺點 | 沒記工時的項次不能標完成 |
| 開發成本 | **低**。狀態加兩個日期 |
| 維護成本 | **低** |

#### 其他可選方案

**方案 B：無工時也可標記完成，實際結束留空**

| 面向 | 說明 |
|------|------|
| 優點 | 彈性 |
| 缺點 | 「實際結束＝最後工時日」對不上 |
| 開發成本 | **低** |
| 維護成本 | **中** |

**方案 C：不做標記完成；有工時就持續更新實際結束＝最後工時日**

| 面向 | 說明 |
|------|------|
| 優點 | 少一個按鈕 |
| 缺點 | 違反補充「標記完成時才取實際結束」 |
| 開發成本 | **低** |
| 維護成本 | **中** |

#### 建議選擇

> 建議選擇 **A**。

原因：與補充 §5.6 字面一致，實際結束不會憑空產生。

#### 使用者選擇

□ A — 詳情可標記完成；無工時不可標記（推薦）

☑ B — 無工時也可完成，實際結束可空

□ C — 不做標記完成，實際結束跟著最後工時日走

□ 自行補充
