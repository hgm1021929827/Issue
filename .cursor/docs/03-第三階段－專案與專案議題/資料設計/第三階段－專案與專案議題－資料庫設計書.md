## 一、資料庫設計理念

個人單人系統，結構求清楚、好改。本輪對應 SA 兩個新邏輯實體：`project`、`projectIssue`。既有 `major_category`、`sub_category`、`issue`、`issue_plan`、`issue_todo` 不新增欄位（正式議題不綁專案）。

不用分片、不用讀寫分離。主鍵一律 `BIGINT AUTO_INCREMENT`。表名與欄位 `snake_case`。C# 實體 PascalCase 對應 underscore。庫名仍為 `issue_tracker`，charset `utf8mb4`。

不預埋廠商、工時、負責人、是否完成。`itemCount` 為查詢計算，不存欄。

## 三、Table 詳細設計

### project

中文名稱：專案

用途：儲存使用者手建的專案主資料。畫面顯示 `project_code`。行事曆到期日用 `due_date`；`start_date` 不上曆。

#### 欄位設計

| 欄位名稱 | 中文名稱 | 資料型態 | 驗證限制 | 是否允許 NULL | 預設值 | 說明 |
| -------- | -------- | -------- | -------- | ------------- | ------ | ---- |
| project_id | 編號 | BIGINT | PRIMARY KEY | 否 | AUTO_INCREMENT | 主鍵；系統內部識別 |
| project_code | 專案代號 | VARCHAR(50) | NOT NULL；UNIQUE | 否 | — | 對應邏輯 `code`；使用者輸入；全系統唯一（忽略大小寫另見應用層） |
| project_name | 專案名稱 | VARCHAR(200) | NOT NULL | 否 | — | 對應邏輯 `name` |
| description | 工作說明 | VARCHAR(4000) | NOT NULL | 否 | `''` | 無則空字串 |
| major_category_id | 大分類 | BIGINT | NOT NULL；FK | 否 | — | 指向 major_category |
| sub_category_id | 小分類 | BIGINT | FK | 是 | NULL | 空白小分類；若有值須屬該大分類（應用層） |
| start_date | 預計開始日 | DATE | — | 是 | NULL | 若與 due_date 都有值則不可晚於完成日（應用層） |
| due_date | 預計完成日 | DATE | — | 是 | NULL | 行事曆到期日 |
| created_at | 建立時間 | DATETIME | NOT NULL | 否 | CURRENT_TIMESTAMP | — |
| updated_at | 更新時間 | DATETIME | NOT NULL | 否 | CURRENT_TIMESTAMP | 更新時刷新 |

C# 實體建議：`Project`；`ProjectId`、`ProjectCode`、`ProjectName`、`Description`、`MajorCategoryId`、`SubCategoryId`、`StartDate`、`DueDate`、`CreatedAt`、`UpdatedAt`。

### project_issue

中文名稱：專案議題

用途：隸屬一筆專案的議題列。唯一語意為專案＋項次。不可改掛專案（應用層不提供改 `project_id`）。

#### 欄位設計

| 欄位名稱 | 中文名稱 | 資料型態 | 驗證限制 | 是否允許 NULL | 預設值 | 說明 |
| -------- | -------- | -------- | -------- | ------------- | ------ | ---- |
| project_issue_id | 編號 | BIGINT | PRIMARY KEY | 否 | AUTO_INCREMENT | 主鍵 |
| project_id | 所屬專案 | BIGINT | NOT NULL；FK | 否 | — | 指向 project；刪專案時 CASCADE |
| seq_no | 項次 | VARCHAR(50) | NOT NULL | 否 | — | 對應邏輯 `seqNo`；同一專案內唯一（忽略大小寫另見應用層） |
| title | 標題 | VARCHAR(200) | NOT NULL | 否 | — | — |
| content | 內容 | VARCHAR(4000) | NOT NULL | 否 | `''` | 無則空字串 |
| major_category_id | 大分類 | BIGINT | NOT NULL；FK | 否 | — | 指向 major_category |
| sub_category_id | 小分類 | BIGINT | FK | 是 | NULL | 空白小分類；若有值須屬該大分類（應用層） |
| start_date | 預計開始日 | DATE | — | 是 | NULL | 不上行事曆；起迄規則同專案 |
| due_date | 預計完成日 | DATE | — | 是 | NULL | 行事曆到期日 |
| created_at | 建立時間 | DATETIME | NOT NULL | 否 | CURRENT_TIMESTAMP | — |
| updated_at | 更新時間 | DATETIME | NOT NULL | 否 | CURRENT_TIMESTAMP | 更新時刷新 |

C# 實體建議：`ProjectIssue`；`ProjectIssueId`、`ProjectId`、`SeqNo`、`Title`、`Content`、`MajorCategoryId`、`SubCategoryId`、`StartDate`、`DueDate`、`CreatedAt`、`UpdatedAt`。

既有 `major_category`、`sub_category` 欄位仍以第一階段設計書為準，本輪不重出欄位表。

## 四、Table 關聯

新增：

- `project.major_category_id` → `major_category.major_category_id`（ON DELETE RESTRICT）
- `project.sub_category_id` → `sub_category.sub_category_id`（ON DELETE RESTRICT）
- `project_issue.project_id` → `project.project_id`（ON DELETE CASCADE）
- `project_issue.major_category_id` → `major_category.major_category_id`（ON DELETE RESTRICT）
- `project_issue.sub_category_id` → `sub_category.sub_category_id`（ON DELETE RESTRICT）

刪專案時其專案議題隨 CASCADE 刪除。刪大／小分類由應用層先 COUNT 正式議題＋專案＋專案議題，使用中則 409；資料庫 RESTRICT 作為第二道防線。

既有 issue 相關 FK 不變。`project` 與 `issue` 無 FK。

---

## 五、Index 建議

- UNIQUE (`project_code`) on `project`
- INDEX (`major_category_id`) on `project`
- INDEX (`due_date`) on `project`
- UNIQUE (`project_id`, `seq_no`) on `project_issue`
- INDEX (`major_category_id`) on `project_issue`
- INDEX (`due_date`) on `project_issue`

---

## 六、Constraint

- 專案代號全系統唯一（上列 UNIQUE）。應用層再以忽略大小寫檢查（對齊 `issue_no`、大分類名稱）。
- 項次在同一 `project_id` 下唯一（上列 UNIQUE）。應用層再以忽略大小寫檢查。
- 應用層：`sub_category` 的大分類必須等於該列的 `major_category_id`。
- 應用層：`start_date` 與 `due_date` 都有值時，開始日不可晚於完成日。
- 應用層：更新專案議題不得改 `project_id`。

若連線排序規則已是 ci，UNIQUE 已能擋多數大小寫重複；仍須保留應用層 ToLower，與第一階段一致。

---

## 七、資料生命週期

- 專案：使用者新增／改／刪。刪除即永久刪除，連同其全部 `project_issue`。無回收筒。無種子列。
- 專案議題：只在所屬專案底下新增／改／刪；單獨刪一列不刪專案。
- 大／小分類：生命週期仍依第一階段；刪除前 COUNT 須含專案與專案議題引用。
- 行事曆標記無獨立表；讀 `due_date`。

---

## 八、命名規範

表與欄位 snake_case。C#：`ProjectId` 對 `project_id`，`ProjectCode` 對 `project_code`，`SeqNo` 對 `seq_no`。

JSON／邏輯屬性仍為 SA 的 camelCase（`code`、`seqNo`）；資料表用上表實體名，不把 JSON 名直接當欄名。

---

## 九、設計決策

- 表名用 `project_issue` 而非再叫 `issue`，避免與正式議題表混淆。
- `project_code`／`seq_no` 對齊 `issue_no` 的 VARCHAR(50) 手填識別。
- `description`／`content` 用 NOT NULL 預設空字串，避免 null／空混用。
- 完成狀態不建欄，進度只存在小分類 FK。
- 既有庫目前 `EnsureCreated()` 只在空庫建表。已有 `issue_tracker` 時 RD **必須**補建本輪兩表（例如啟動時對新實體建表、一次性 DDL，或改 Migration）。不得假定 EnsureCreated 會幫舊庫加表。
- 不預埋廠商、工時欄，以免空欄與後續匯入規則衝突。
