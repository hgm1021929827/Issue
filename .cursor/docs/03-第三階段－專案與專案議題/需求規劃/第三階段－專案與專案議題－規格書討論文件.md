## 一、討論前提

下列前提若不同意，請在對應題目選「自行補充」：

- 本系統仍為**個人使用**；使用者可見文案繁體中文；單人、無登入。
- **本階段只做**專案、專案議題。下列已凍結、**不在本文件勾選**：Excel 匯入、工作表規則、負責人員／處理人篩選、日期工時、Excel 備註工時比對、匯入異常與跳轉、臨時工作。
- **不改**第一階段正式文件。分類、正式議題、TODO、首頁清單與行事曆既有行為維持；本階段只**增量**（例如刪小分類時多檢查專案資料）。
- 第一階段之後，大分類已改為使用者可維護（種子「預約／議題分類」），顏色在小分類。本階段若用分類，沿用同一套，不另做專案專用色票。
- 來源檔第五章的「專案」幾乎是 Excel 匯入前置；第十章把廠商、成員列在再下一階段。不含匯入時，手動 CRUD 欄位必須在本文件勾選，不得臆測。
- 角色提示中的 `category` 僅為格式示範。前後端切分屬 SA／Tech Spike，不在本文件勾選。

## 三、待確認項目

### Q1：專案議題與正式議題是不是同一種資料


#### 問題描述

來源檔把「議題、專案、專案議題」並列為三種工作類型；Excel「工作項目」對專案、「議題單」對專案議題。第一階段「正式議題」已可日常使用。本輪的專案議題，要獨立成一種資料，還是變成「掛在專案底下的正式議題」？


#### 推薦方案 A：獨立資料；一筆專案底下多筆專案議題；正式議題本輪不綁專案

說明：專案是容器；專案議題只活在該專案裡。首頁正式議題清單不變。之後 Excel「議題單」對應專案議題，不必改第一階段議題模型。

| 面向 | 說明 |
|------|------|
| 推薦原因 | 對齊來源三種工作類型；本輪範圍清楚；不重寫已結案的議題契約 |
| 優點 | 之後匯入「議題單」有對應實體；正式議題與專案議題不會混在同一清單 |
| 缺點 | 兩種「議題」畫面與欄位可能部分相似，要靠導覽與用詞區隔 |
| 開發成本 | **中**。新實體與專案詳情內清單，但不改正式議題 API 語意 |
| 維護成本 | **低**。界線清楚，之後匯入可掛在專案議題上 |


#### 其他可選方案

**方案 B：專案議題＝正式議題加上「所屬專案」**

| 面向 | 說明 |
|------|------|
| 優點 | 少一種資料；TODO、行事曆可沿用 |
| 缺點 | 來源「議題單」與日常正式議題混在一起；項次／專案編號規則會侵入第一階段議題；首頁清單語意變模糊 |
| 開發成本 | **中**。要改既有議題欄位與清單過濾 |
| 維護成本 | **高**。第一階段契約被本輪撐開 |

**方案 C：本輪只做專案本體，專案議題用備註或無識別的明細列**

| 面向 | 說明 |
|------|------|
| 優點 | 本輪最小 |
| 缺點 | 沒有「項次」唯一鍵，下一輪 Excel 議題單仍要重做模型 |
| 開發成本 | **低**。少一個完整實體 |
| 維護成本 | **高**。下一輪幾乎重做 |


#### 建議選擇

> 建議選擇 **A**。

原因：階段名稱就是「專案、專案議題」；來源已當兩種資料。不要把已結案的正式議題改成專案子項。


#### 使用者選擇

☑ A — 專案議題獨立，正式議題本輪不綁專案（推薦）

□ B — 專案議題就是掛專案的正式議題

□ C — 本輪只有專案，議題用備註／無識別明細

□ 自行補充

### Q2：專案本輪要哪些欄位（不含廠商、工時表、負責人）


#### 問題描述

來源「完整主資料」很長，但匯入、工時、負責人已凍結不做。手動新增一筆專案時，哪些欄位本輪就要能填、能改、能列在清單？

第一階段議題是：使用者輸入唯一**編號**＋標題等。來源專案同時有「專案編號」與「專案代號」。


#### 推薦方案 A：代號當畫面唯一鍵；名稱必填；說明與預計起迄選填

本輪專案欄位：

| 欄位 | 規則 |
|------|------|
| 專案代號 | 使用者輸入、必填、全系統唯一（忽略大小寫）；清單與詳情顯示此代號 |
| 專案名稱 | 必填 |
| 工作說明 | 可空 |
| 預計開始日、預計完成日 | 可空；僅日期 |

系統內部另有識別，不給使用者填。本輪**不做**：第二個「專案編號」欄、工作代號、計畫人天、廠商、負責人員、實際開始／結束、日期工時、目前工時累計。之後匯入可用「代號」對應來源的專案編號或再加欄，不在本輪預埋空欄。

| 面向 | 說明 |
|------|------|
| 推薦原因 | 夠日常手建專案；對齊議題「手填唯一編號」；避開匯入／工時／成員依賴 |
| 優點 | 清單能搜代號與名稱；預計日可供之後上曆，本輪不必做行事曆 |
| 缺點 | 來源「編號＋代號」兩欄本輪合成一欄，匯入階段可能要加欄或對應規則 |
| 開發成本 | **低**。一般表單 CRUD |
| 維護成本 | **低**。欄位少，下一輪加欄即可 |


#### 其他可選方案

**方案 B：能手動填的來源欄都做（仍不含廠商、負責人、日期工時）**

另加：工作代號、計畫人天、實際開始、實際結束（皆手填，不由工時推算）。

| 面向 | 說明 |
|------|------|
| 優點 | 較接近第五章完整主資料 |
| 缺點 | 實際起迄在來源是由工時算出；本輪手填之後匯入／工時階段要改規則，容易做假 |
| 開發成本 | **中**。欄位與驗證較多 |
| 維護成本 | **中**。與第七章「實際日由工時推」之後會衝突 |

**方案 C：極簡，只有名稱與說明，沒有代號**

| 面向 | 說明 |
|------|------|
| 優點 | 最快能建檔 |
| 缺點 | 沒有業務識別，6.3「專案編號＋項次」下一輪仍缺左半邊 |
| 開發成本 | **低** |
| 維護成本 | **中**。幾乎立刻要補代號 |


#### 建議選擇

> 建議選擇 **A**。

原因：本輪目標是手動維護，不是一次對齊 Excel 主檔。實際日期與人天留給工時階段，避免先手填再被計算覆寫。


#### 使用者選擇

☑ A — 代號（唯一）＋名稱＋說明＋預計起迄；不做人天／實際日／工作代號（推薦）

□ B — 再加工作代號、計畫人天、實際起迄（手填）

□ C — 只有名稱與說明，沒有代號

□ 自行補充

### Q3：本輪要不要廠商


#### 問題描述

匯入前置把廠商當必填，下拉來自客戶公司，旁邊還有快捷新增。成員／客戶公司在第十章是「再下一階段」。沒有客戶公司表時，專案還要不要有廠商？


#### 推薦方案 A：本輪專案沒有廠商欄

說明：名稱與代號即可建立專案。廠商、快捷新增、客戶窗口整包放到成員階段，匯入階段再改為必填。

| 面向 | 說明 |
|------|------|
| 推薦原因 | 對齊階段開立與第十章切分；避免本輪做一個不完整的客戶主檔 |
| 優點 | 範圍不破；匯入階段一次做對下拉與快捷新增 |
| 缺點 | 現在畫面上看不到廠商，與來源 5.1 不完全相同 |
| 開發成本 | **低**。本輪少一個關聯 |
| 維護成本 | **低** |


#### 其他可選方案

**方案 B：廠商為自由文字，可空**

| 面向 | 說明 |
|------|------|
| 優點 | 現在就能記廠商名 |
| 缺點 | 之後改下拉要遷資料、對不齊公司主檔 |
| 開發成本 | **低** |
| 維護成本 | **中**。雙軌（文字 vs 主檔） |

**方案 C：本輪就做客戶公司清單＋下拉＋快捷新增**

| 面向 | 說明 |
|------|------|
| 優點 | 對齊 5.2 |
| 缺點 | 把再下一階段的成員維護提前，超出「只要專案、專案議題」 |
| 開發成本 | **高**。等於加一條客戶主檔 |
| 維護成本 | **中** |


#### 建議選擇

> 建議選擇 **A**。

原因：廠商不是「專案議題」本體；做一半的文字欄會害下一輪遷移。


#### 使用者選擇

☑ A — 本輪無廠商（推薦）

□ B — 自由文字廠商，可空

□ C — 本輪做客戶公司下拉與快捷新增

### Q4：專案議題怎麼識別、本輪哪些欄位


#### 問題描述

來源 6.3：專案議題唯一鍵是「專案編號＋項次」，不得只使用項次。本輪沒有 Excel「處理人」篩選。詳情裡一筆專案議題要能新增、改、刪。


#### 推薦方案 A：項次手填；同一專案內不可重複；標題必填；內容與預計起迄選填

| 欄位 | 規則 |
|------|------|
| 所屬專案 | 必屬一筆專案；不可改掛到其他專案（本輪若要改掛請選自行補充） |
| 項次 | 使用者輸入、必填；**同一專案內**不可重複（忽略大小寫）；不同專案可以有相同項次 |
| 標題 | 必填 |
| 內容 | 可空 |
| 預計開始日、預計完成日 | 可空；僅日期 |

畫面唯一顯示可為「專案代號＋項次」。沒有全系統另一套「專案議題編號」。沒有處理人、工時、實際起迄。

| 面向 | 說明 |
|------|------|
| 推薦原因 | 直接對齊 6.3；匯入議題單時左半邊用專案代號、右半邊用項次 |
| 優點 | 不依賴 Excel 也能手建議題單列 |
| 缺點 | 項次格式（純數字或可含文字）來源未寫，規格書將假設允許一般字串、長度上限與議題編號同級（50） |
| 開發成本 | **低**。專案詳情內子清單 CRUD |
| 維護成本 | **低** |


#### 其他可選方案

**方案 B：項次由系統依專案自動流水（1、2、3…），不可改**

| 面向 | 說明 |
|------|------|
| 優點 | 不會打錯重複項次 |
| 缺點 | 與 Excel 既有項次對不齊時匯入很痛 |
| 開發成本 | **低** |
| 維護成本 | **中**。匯入階段可能要改成可指定項次 |

**方案 C：另加全系統唯一「專案議題編號」（像正式議題編號），項次仍要**

| 面向 | 說明 |
|------|------|
| 優點 | 清單、跳轉可用單一編號 |
| 缺點 | 本輪多一個必填識別，與 6.3 重複 |
| 開發成本 | **中** |
| 維護成本 | **中** |


#### 建議選擇

> 建議選擇 **A**。

原因：唯一鍵語意先對齊來源；項次給你填才能對日後 Excel。規格將註明項次為字串、同專案不可重。


#### 使用者選擇

☑ A — 手填項次（同專案唯一）＋標題＋內容＋預計起迄（推薦）

□ B — 項次系統流水，不可改

□ C — 再加全系統唯一專案議題編號

□ 自行補充

### Q5：專案、專案議題要不要用現有大小分類


#### 問題描述

來源 4.3：刪小分類前須檢查是否被專案、專案議題使用。第一階段刪除只檢查正式議題。本輪要不要讓專案／專案議題也選大分類、小分類（同一套分類設定，含空白小分類規則）？


#### 推薦方案 A：兩者都可以選大小分類；刪分類時一併檢查使用中筆數

說明：表單與議題相同：大分類必選、小分類可空；空白時畫面顯示大分類名稱、顏色用空白備選色 `#8FA8C8`。預設大分類比照新增議題：優先「議題分類」，否則「預約」，否則第一個大分類。刪大分類／小分類時，除正式議題外，若有專案或專案議題使用則不可刪，並提示筆數。

| 面向 | 說明 |
|------|------|
| 推薦原因 | 對齊 4.3；狀態與顏色不必另做一套；完成可用你自己的「已完成」大分類（見 Q6） |
| 優點 | 分類設定一處維護；清單可用色標 |
| 缺點 | 專案與議題共用分類，名稱上可能混在一起（例如「預約」也出現在專案上） |
| 開發成本 | **中**。表單＋刪除檢查擴大，不新增分類種類 |
| 維護成本 | **低** |


#### 其他可選方案

**方案 B：只有專案議題有分類；專案沒有**

| 面向 | 說明 |
|------|------|
| 優點 | 專案當檔案夾、狀態只在議題列 |
| 缺點 | 4.3 仍點名專案也會用到小分類；本輪不建之後刪除檢查仍缺一角 |
| 開發成本 | **中** |
| 維護成本 | **低** |

**方案 C：本輪都不要分類**

| 面向 | 說明 |
|------|------|
| 優點 | 表單更短 |
| 缺點 | 沒有狀態色；4.3 本輪無法落地；完成標記要另做（Q6） |
| 開發成本 | **低** |
| 維護成本 | **中**。下一輪再補分類與刪除檢查 |


#### 建議選擇

> 建議選擇 **A**。

原因：來源已假設專案資料會引用小分類 ID。共用現有分類，比新做專案狀態枚舉更省，也讓刪除規則一次做對。


#### 使用者選擇

☑ A — 專案與專案議題都用現有大小分類；刪分類加查使用中（推薦）

□ B — 只有專案議題有分類

□ C — 本輪都不要分類

□ 自行補充

### Q6：專案／專案議題怎樣算完成


#### 問題描述

來源第七章「專案標記完成」是搭配日期工時的。第一階段正式議題沒有獨立完成核取，狀態靠大分類。大分類現在已是使用者自訂，系統不再內建「已完成」四固定值。


#### 推薦方案 A：與正式議題相同，完成只靠改大分類；不做獨立核取

說明：沒有「專案完成」方塊。你把大分類改到自己定義的完成類（例如自建「已完成」）即表示完成。不因 TODO（本輪可能沒有，見 Q7）或到期日自動改分類。

| 面向 | 說明 |
|------|------|
| 推薦原因 | 與現行議題一致；不引入第二套完成模型 |
| 優點 | 學一次即可；工時階段再定義「標記完成時取最後工時日」 |
| 缺點 | 若你沒有名為完成的大分類，畫面上沒有統一「已完成」過濾 |
| 開發成本 | **低**。不另做核取 |
| 維護成本 | **低** |


#### 其他可選方案

**方案 B：專案與專案議題各有「是否完成」核取，與分類獨立**

| 面向 | 說明 |
|------|------|
| 優點 | 不必靠分類名稱 |
| 缺點 | 第一階段已拒絕「議題層獨立完成核取」；專案若做核取，兩種工作完成規則不一致 |
| 開發成本 | **低** |
| 維護成本 | **中** |

**方案 C：本輪不表達完成，只顯示預計日**

| 面向 | 說明 |
|------|------|
| 優點 | 最少 |
| 缺點 | 清單難分進行中／已結束 |
| 開發成本 | **低** |
| 維護成本 | **低** |


#### 建議選擇

> 建議選擇 **A**（若 Q5 選 C，則改以方案 B 為正式規格預設，並在規格開頭註明依賴）。

原因：完成模型不要跟正式議題分叉。工時推算實際結束日屬於已凍結的後續階段。


#### 使用者選擇

☑ A — 無獨立核取；**完成／進度靠改小分類**（使用者確認：不是改大分類）

□ B — 獨立「是否完成」核取

□ C — 本輪不表達完成

□ 自行補充

補充：大分類仍必選（Q5＝A），用來分組；狀態與顏色以小分類為準。系統不把任何小分類名稱寫死為「已完成」。

### Q7：本輪要不要 TODO


#### 問題描述

來源第十章提到「專案底下的一般 TODO」（預約連線處理事項）。第一階段 TODO 樹掛在正式議題。專案、專案議題本輪要不要也能拆 TODO？


#### 推薦方案 A：本輪專案與專案議題都沒有 TODO

說明：詳情只編輯主資料與（Q1＝A 時）專案議題清單。需要追蹤的 TODO、專案下一般 TODO 仍列未來規劃。

| 面向 | 說明 |
|------|------|
| 推薦原因 | 範圍只鎖定兩種主資料；TODO 樹已在議題驗證過，之後可再掛 |
| 優點 | 驗收邊界清楚；不複製一套樹到兩個新實體 |
| 缺點 | 專案詳情暫時不能勾事項 |
| 開發成本 | **低**。本輪不做樹 |
| 維護成本 | **低** |


#### 其他可選方案

**方案 B：只有專案議題有與正式議題相同的多層 TODO（含父項自動完成）**

| 面向 | 說明 |
|------|------|
| 優點 | 專案議題可拆工 |
| 缺點 | 等於把 WT-F04／F05 再做一次掛載；本輪變厚 |
| 開發成本 | **中**。複用元件仍要接新所屬 |
| 維護成本 | **中** |

**方案 C：專案與專案議題都有 TODO 樹**

| 面向 | 說明 |
|------|------|
| 優點 | 對齊來源「專案底下一般 TODO」 |
| 缺點 | 超出本輪「只要專案、專案議題」的主資料交付；預約尚未開始 |
| 開發成本 | **高**。兩個掛載點 |
| 維護成本 | **中** |


#### 建議選擇

> 建議選擇 **A**。

原因：先讓專案與專案議題能建檔、能進詳情。TODO 掛專案是預約章節的前置，放到之後階段較乾淨。


#### 使用者選擇

☑ A — 本輪都沒有 TODO（推薦）

□ B — 只有專案議題有多層 TODO

□ C — 專案與專案議題都有 TODO

□ 自行補充

### Q8：放在哪個畫面；要不要上首頁行事曆


#### 問題描述

現有導覽：首頁、分類設定、新增議題。來源假設已有專案詳情頁。首頁行事曆目前是議題到期日＋預計項目。專案預計完成日要不要上同一本日曆？


#### 推薦方案 A：導覽加「專案」；專案清單＋詳情（詳情內維護專案議題）；不上首頁清單、不上行事曆

說明：首頁仍只服務正式議題。專案清單可依大分類篩選（若 Q5 有分類）。新增專案、點列進詳情；詳情可新增／編輯／刪除專案議題。視覺對齊粉彩規格；確認刪除用 `dialog`。

| 面向 | 說明 |
|------|------|
| 推薦原因 | 不把行事曆再加重（已有雙視角）；專案有獨立入口 |
| 優點 | 與正式議題空間分開，符合三種工作類型 |
| 缺點 | 到期專案不會出現在首頁月曆 |
| 開發成本 | **中**。新清單＋詳情頁，行事曆不改 |
| 維護成本 | **低** |


#### 其他可選方案

**方案 B：A 的畫面，再加上：有預計完成日的專案（及可選專案議題）出現在現有行事曆**

| 面向 | 說明 |
|------|------|
| 優點 | 一眼看到到期專案 |
| 缺點 | 月曆已有到期日／預計項目，再加專案易擠；標記規則（顯示代號或名稱）要另定 |
| 開發成本 | **中**。行事曆資料源擴大，屬 Spike 風險 |
| 維護成本 | **中** |

**方案 C：首頁清單把正式議題與專案混在同一列表**

| 面向 | 說明 |
|------|------|
| 優點 | 少一個導覽 |
| 缺點 | 兩種資料欄位不同，清單難共用；破壞第一階段首頁驗收語意 |
| 開發成本 | **中** |
| 維護成本 | **高** |


#### 建議選擇

> 建議選擇 **A**。

原因：本輪先把專案當獨立工作區。行事曆加專案可當下一輪或本階段 Should，不必擋 MVP。若你選 B，規格會把行事曆標為待 Tech Spike。


#### 使用者選擇

□ A — 獨立專案清單／詳情；不上首頁、不上行事曆（推薦）

☑ B — 獨立頁面，且預計完成日上現有行事曆

□ C — 首頁清單混著顯示議題與專案

□ 自行補充

### Q9：刪除專案時，底下的專案議題怎麼辦


#### 問題描述

刪正式議題會連 TODO 一起刪（確認後）。刪大分類若仍有議題則禁止。專案是容器時，刪專案要禁止還是連刪專案議題？


#### 推薦方案 A：有專案議題就不可刪專案，並提示筆數；專案議題可單獨刪（確認）

說明：對齊「分類使用中不可刪」。要刪專案須先清議題列。刪專案議題不可復原（本輪無回收筒）。

| 面向 | 說明 |
|------|------|
| 推薦原因 | 避免誤刪一整包議題單；與刪分類經驗一致 |
| 優點 | 資料較不易一次沒掉 |
| 缺點 | 棄用專案要先逐筆刪議題 |
| 開發成本 | **低** |
| 維護成本 | **低** |


#### 其他可選方案

| 面向 | 說明 |
|------|------|
| 優點 | 對齊刪議題連刪 TODO，收尾快 |
| 缺點 | 一次刪多列，復原不了 |
| 開發成本 | **低** |
| 維護成本 | **低** |

**方案 C：刪除進回收筒，可恢復**

| 面向 | 說明 |
|------|------|
| 優點 | 可反悔 |
| 缺點 | 第一階段已不做回收筒；本輪新開回收會擴大範圍 |
| 開發成本 | **高** |
| 維護成本 | **中** |

> 建議選擇 **A**。

原因：專案議題是獨立工作列（Q1＝A），不是 TODO 那種純拆解。禁止連刪比較不容易手滑。若你希望專案當資料夾一次丟掉，選 B。

### Q10：正式議題本輪要不要能選「所屬專案」


#### 問題描述

即使 Q1 選 A（專案議題獨立），仍可選擇讓**既有正式議題**選填所屬專案，方便從專案詳情看到相關日常議題。來源沒有寫「正式議題屬於專案」。


#### 推薦方案 A：本輪正式議題不增加所屬專案

說明：專案詳情只列出專案議題。日常議題與專案兩條線。之後若要綁，再開階段或增量。

| 面向 | 說明 |
|------|------|
| 推薦原因 | 不改第一階段議題欄位契約；範圍只落在新實體 |
| 優點 | 熔斷風險低；QA 回歸面較小 |
| 缺點 | 不能從專案點到相關正式議題 |
| 開發成本 | **低**。議題 API 不動 |
| 維護成本 | **低** |


#### 其他可選方案

**方案 B：正式議題可選填所屬專案；專案詳情加「相關正式議題」列表（唯讀跳轉或可編）**

| 面向 | 說明 |
|------|------|
| 優點 | 專案可當工作夾，串起日常議題 |
| 缺點 | 要改議題表單與清單；接近改第一階段契約（本階段增量可以，但回歸變大） |
| 開發成本 | **中** |
| 維護成本 | **中** |

**方案 C：專案議題可一鍵轉成正式議題（複製或搬移）**

| 面向 | 說明 |
|------|------|
| 優點 | 匯入列可升級成日常追蹤 |
| 缺點 | 轉換規則來源沒有；本輪易臆測 |
| 開發成本 | **中** |
| 維護成本 | **高** |

> 建議選擇 **A**。

原因：本輪把「專案／專案議題」做完整即可。正式議題綁專案是額外產品決定，不擋 MVP。
