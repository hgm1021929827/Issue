# 第三階段－專案與專案議題－技術可行性評估

**角色：** RD（Tech Spike，非正式開發）  
**日期：** 2026-09-02  
**依據：** 規格書 §8.5 待評估項、系統設計草擬 API／UI

## 結論

**可行。** 沿用既有 React SPA、ASP.NET Core 9 API、MySQL、粉彩 token。不需新月曆套件，不需改第一階段議題／TODO 契約。

本輪無須於 Spike 交付正式功能程式；下列供 SA 定稿。

## 評估項目

| 項目 | 結果 | 說明 |
|------|------|------|
| 專案／專案議題 CRUD | 可行 | 對齊既有 Issue 表單與 Category 下拉；新增 Controller／Service 即可。 |
| 代號／項次忽略大小寫唯一 | 可行 | 與 `issueNo`、大分類名稱相同：應用層 `ToLower` 比對；DA 可再加唯一約束。 |
| 刪專案連刪專案議題 | 可行 | 服務層先刪子列或資料庫 CASCADE；確認 dialog 用 `itemCount`。 |
| 分類刪除擴大 COUNT | 可行 | `CategoryService` 現只 COUNT `Issues`；再加 project／projectIssue 兩段即可。 |
| 行事曆三種到期資料 | 可行 | 擴充既有 `GET /issues/calendar` 與 `IssueCalendarItemDto`：加 `source`、`label`、`projectId`。首頁已一次取 calendar。 |
| 到期日／預計項目過濾 | 可行 | `MonthCalendar` 已用 `kind === "plan"` 對 `views.plan`，其餘當 due。專案列只出 `kind: "due"` 即自動跟到期日視角，不會進預計項目。 |
| 點擊跳轉 | 可行 | 依 `source` 改 `Link`：`/issues/{id}`、`/projects/{id}`、`/projects/{projectId}?item={id}`。詳情用 `useSearchParams` 高亮列。 |
| 同日擁擠、截斷、可點性 | 可行 | 維持自製 Grid；格內標記區設最大高度並 `overflow-y: auto`；文字 CSS 截斷；lucide 圖示＋`aria-label` 區分類型。不必 FullCalendar，本輪不做「+N」彈層。 |
| 視覺 | 可行 | 新頁沿用 `styles.css` token 與現有卡片／表單／dialog，不另引入元件庫。 |
| id 撞號 | 可行 | 不同表 AUTO_INCREMENT 可能同號；列表與月曆 key 必須含 `source`。 |
