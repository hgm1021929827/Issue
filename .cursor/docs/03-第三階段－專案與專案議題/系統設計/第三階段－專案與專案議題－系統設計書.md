# 一、系統架構

沿用第一階段：

- **frontend：** React（Vite）SPA，埠 `5173`
- **backend：** ASP.NET Core 9 API Controller，埠 `5080`
- **database：** MySQL 8，庫名 `issue_tracker`

瀏覽器只打後端 HTTP API。EF Core（Pomelo）存取 MySQL。無登入、無 JWT。

統一回應：

```json
{ "code": 200, "message": "success", "data": {} }
```

成功 HTTP 200 且 `code === 200`。業務錯誤 HTTP 400／404／409，body 同上（`data` 可 null）。前端以 `code === 200` 判斷成功。JSON 屬性 **camelCase**。路徑無 `/api` 前綴。

新畫面重用 `frontend/src/styles.css` 的 `:root` token（第二階段視覺規格）。確認刪除用 HTML `dialog`。

# 二、模組拆分

| 模組 | 職責 |
|------|------|
| 分類（既有增量） | 刪大／小分類時，除正式議題外，加計專案、專案議題使用筆數 |
| 專案 | 專案 CRUD；刪除時一併刪其專案議題 |
| 專案議題 | 隸屬專案的清單與 CRUD；不可改掛專案 |
| 行事曆（既有增量） | `GET /issues/calendar` 在到期日資料中併入有預計完成日的專案與專案議題 |

前端頁面增量：專案清單、專案新增、專案詳情（含專案議題區）。首頁議題清單不混入專案。導覽加「專案」。

不實作：Excel、廠商、工時、TODO 掛專案、正式議題綁專案、預計項目拖專案。

# 三、功能流程

對齊規格第六章。

- 預設大分類與新增正式議題相同：名稱「議題分類」→ 否則「預約」→ 否則列表第一筆。前端用既有 `GET /majorCategories` 決定，後端只驗證 id 存在。
- 切換大分類：前端將不屬於新大分類的 `subCategoryId` 改為 `null` 再送出；後端若小分類不屬於該大分類則 400。
- 狀態／完成：只寫 `subCategoryId`。無 `isCompleted`。不因到期或子列自動改分類。
- 刪專案：服務層先刪該專案全部專案議題再刪專案（物理 CASCADE 由 DA 定，語意必須整包消失）。
- 行事曆「到期日」視角顯示 `kind === "due"` 的正式議題、專案、專案議題；「預計項目」仍僅 `kind === "plan"` 的正式議題，不得為專案產生 plan。

**PJ-F08 點擊專案議題（規格授權 SA 定互動）：** 導向 `/projects/{projectId}?item={projectIssueId}`。詳情載入後捲動至該列、加上高亮，並打開該筆編輯區（同一頁表單或列內展開）。找不到項次則仍開專案詳情，頁內橫幅「找不到該專案議題」。

# 四、API 規劃

既有 `/majorCategories`、`/subCategories`、`/issues`、`/todos` 契約維持。下列為新增或標明增量。

色彩規則與議題相同：清單／月曆用小分類色；無小分類時 `#8FA8C8`。`majorCategoryColor` 與 `subCategoryColor` 在無小分類時同為該備選色。

### 4.1 專案

| 名稱 | 方法 | 路徑 | Request | Response data | Error |
|------|------|------|---------|---------------|-------|
| 列表 | GET | `/projects?majorCategoryId=` | query 可省略 | `ProjectListItem[]` | — |
| 單筆 | GET | `/projects/{id}` | 無 | `ProjectDetail`（含 `items`） | 404 |
| 新增 | POST | `/projects` | `ProjectWrite` | `ProjectDetail` | 400 驗證；409 代號重複 |
| 更新 | PUT | `/projects/{id}` | `ProjectWrite` | `ProjectDetail` | 404；400；409 代號重複 |
| 刪除 | DELETE | `/projects/{id}` | 無 | `{ deleted: true, itemCount }` | 404 |

`ProjectWrite`：`code`（必填、全系統唯一、忽略大小寫、最長 50）、`name`（必填、最長 200）、`description`（可空字串、最長 4000）、`majorCategoryId`（必填）、`subCategoryId`（可 null）、`startDate`（可 null，`yyyy-MM-dd`）、`dueDate`（可 null，`yyyy-MM-dd`）

驗證：`code`／`name` 去空白後不可空；大分類須存在；若 `subCategoryId` 有值須存在且屬於該大分類；若 `startDate` 與 `dueDate` 都有值，開始不可晚於完成。

`ProjectListItem`：`id`, `code`, `name`, `description`, `majorCategoryId`, `majorCategoryName`, `majorCategoryColor`, `subCategoryId`, `subCategoryName`, `subCategoryColor`, `startDate`, `dueDate`, `itemCount`, `createdAt`, `updatedAt`

`ProjectDetail`：同清單欄位，另加 `items: ProjectIssue[]`（見 4.2）。刪除前確認對話用 `itemCount`（詳情亦可以 `items.length`）。

列表排序：`updatedAt` 新到舊，其次 `id`。`itemCount` 為該專案專案議題筆數。

### 4.2 專案議題

路徑中的 `{projectId}` 必須與該筆實際所屬專案一致，否則 404。

| 名稱 | 方法 | 路徑 | Request | Response data | Error |
|------|------|------|---------|---------------|-------|
| 列表 | GET | `/projects/{projectId}/items` | 無 | `ProjectIssue[]` | 404 專案 |
| 新增 | POST | `/projects/{projectId}/items` | `ProjectIssueWrite` | 該專案完整 `ProjectIssue[]` | 404 專案；400；409 同專案項次重複 |
| 更新 | PUT | `/projects/{projectId}/items/{id}` | `ProjectIssueWrite` | 該專案完整 `ProjectIssue[]` | 404；400；409 |
| 刪除 | DELETE | `/projects/{projectId}/items/{id}` | 無 | 該專案完整 `ProjectIssue[]` | 404 |

寫入成功 `data` 回傳**該專案更新後完整專案議題列表**（方便前端替換）。

`ProjectIssueWrite`：`seqNo`（項次，必填、最長 50）、`title`（必填、最長 200）、`content`（可空字串、最長 4000）、`majorCategoryId`、`subCategoryId`（可 null）、`startDate`、`dueDate`。分類與起迄驗證同 `ProjectWrite`。不可傳 `projectId` 改掛。

`ProjectIssue`：`id`, `projectId`, `projectCode`, `seqNo`, `title`, `content`, `majorCategoryId`, `majorCategoryName`, `majorCategoryColor`, `subCategoryId`, `subCategoryName`, `subCategoryColor`, `startDate`, `dueDate`, `createdAt`, `updatedAt`

`seqNo` 同一 `projectId` 內唯一（忽略大小寫）。列表排序：`seqNo`（字串序）再 `id`。

### 4.3 行事曆增量

既有 `GET /issues/calendar?year=&month=` **繼續使用**，避免首頁打兩支。`data` 仍為陣列，元素擴充如下。正式議題既有欄位保留，前端可漸進改讀新欄。

| 名稱 | 方法 | 路徑 | Request | Response data | Error |
|------|------|------|---------|---------------|-------|
| 行事曆 | GET | `/issues/calendar?year=&month=` | 年月必填 | `CalendarItem[]` | 400 年月無效 |

`CalendarItem`（正式議題列與現況相容，並加 `source`／`label`／`projectId`）：

| 欄位 | 說明 |
|------|------|
| `source` | `issue`／`project`／`projectIssue`。舊前端若忽略此欄，專案列不得誤連 `/issues/{id}`，**本輪前端必須依 source 跳轉** |
| `kind` | 正式議題：`due` 或 `plan`。專案與專案議題：**僅** `due` |
| `id` | 該列主體識別：議題 id／專案 id／專案議題 id（不同實體可能數字相同，鍵須含 `source`） |
| `projectId` | `projectIssue` 必填；`project` 與 `id` 相同可填；`issue` 為 null |
| `planId` | 僅 `kind === "plan"` |
| `label` | 格子顯示：議題＝編號；專案＝代號；專案議題＝`{projectCode} {seqNo}`（中間空白，過長截斷） |
| `issueNo` | 正式議題＝編號；其餘可空或與 `label` 相同（相容舊欄） |
| `title` | 議題標題／專案名稱／專案議題標題 |
| `content` | Hover：議題內容；專案＝名稱（無名稱時說明摘要）；專案議題＝標題 |
| `date` | 該標記所在日 |
| `dueDate` | 到期日視角下與 `date` 同值 |
| `majorCategoryId`, `majorCategoryColor`, `subCategoryColor` | 同議題色票規則 |

查詢範圍：該月 1 日 ≤ 日期 < 次月 1 日。

- `issue`＋`due`：正式議題 `dueDate`
- `issue`＋`plan`：既有預計項目（不變）
- `project`＋`due`：專案 `dueDate` 有值
- `projectIssue`＋`due`：專案議題 `dueDate` 有值

不回傳專案／專案議題的 `startDate`。不為專案建立 plan 列。

### 4.4 分類刪除增量

`DELETE /majorCategories/{id}`、`DELETE /subCategories/{id}` 路徑不變。409 條件改為：正式議題 **或** 專案 **或** 專案議題仍引用則不可刪。

`message` 繁中，須讓人知道與專案有關。建議格式（只列出大於 0 的段）：

`使用中，共 {n} 筆正式議題、{n} 筆專案、{n} 筆專案議題`

大分類另計：該大分類 id 被專案／專案議題的 `majorCategoryId` 引用。小分類計 `subCategoryId`。大分類至少保留一個的規則不變。僅被正式議題使用且專案側為 0 時，行為與現況等價（禁止刪、筆數僅正式議題）。

## 7.2 實體關聯概覽

- majorCategory 1:N project
- majorCategory 1:N projectIssue
- subCategory 1:N project（project.subCategoryId 可空）
- subCategory 1:N projectIssue（可空）
- project 1:N projectIssue
- 既有 majorCategory／subCategory／issue／todo 關聯不變
- project 與 issue **無**關聯

## 7.3 資料流向

分類設定 → 既有大小分類 → 專案／專案議題表單下拉。  
專案寫入 → 專案清單、詳情、行事曆到期列（若有 dueDate）。  
專案議題寫入 → 詳情列表替換、行事曆到期列。  
刪專案 → 該專案所有 projectIssue 消失 → 專案消失 → 月曆對應列消失。  
刪分類 → COUNT issue＋project＋projectIssue → 任一大於 0 則 409。

## 7.4 DA 接手指引

有 Database 持久化。請依 §7.1、§7.1.1、§7.2 產出完整《資料庫設計書》**增量**（新表與既有表關聯；不覆寫第一階段資料庫設計書本文，於第三階段目錄新開）。每個 Table 須有七欄「欄位設計」表。

- 主鍵 BIGINT AUTO_INCREMENT、欄位 snake_case，C# 實體 PascalCase。
- `code`、`(projectId, seqNo)` 須能支撐忽略大小寫唯一（應用層 ToLower 檢查與／或 DA 選定的唯一約束）。
- 刪 project 必須使其 projectIssue 一併不存在（CASCADE 或等價）。
- 刪 major／sub 仍 RESTRICT；應用層先 COUNT。
- 本輪**不要**預埋廠商、工時、負責人欄位。
- 種子：不新增專案範例列。

# 九、例外流程

| 情境 | 行為 |
|------|------|
| 驗證失敗（空白、過長、起迄顛倒、小分類不屬大分類） | 400，message 繁中 |
| 找不到專案／專案議題／路徑專案不符 | 404 |
| 專案代號重複、同專案項次重複 | 409 |
| 分類使用中、只剩一個大分類 | 409，message 含筆數與資料種類 |
| 未處理例外 | 500，message 不暴露堆疊 |

# 十、系統限制

- 單人、無登入
- 專案議題不可改掛專案
- 行事曆預計項目不含專案
- 預計開始日不上行事曆
- 無專案 TODO、無正式議題所屬專案
- 無獨立完成核取；完成不寫死小分類名稱
- 刪除不可復原

# 十一、開發注意事項

- 月曆 React `key` 必須含 `source`（加 `kind`、`id`、`date`），避免專案 id 與議題 id 撞號導致錯鍵。
- `MonthCalendar` 不可再一律 `Link` 到 `/issues/${id}`。
- 分類刪除 COUNT 三類；message 勿只說「議題」而漏專案。
- JSON camelCase；EF 對 DB snake_case。
- 單元測試至少覆蓋：代號忽略大小寫唯一；同專案項次唯一、跨專案可同項次；起迄驗證；刪專案後議題列不在；刪小分類在專案或專案議題引用時 409；行事曆回傳三種 `source` 的 due、不含專案 startDate、不含專案 plan。
- 前端文案區隔「正式議題／專案／專案議題」。

# 十二、已確認決策

- 架構沿用 React SPA + ASP.NET Core JSON API + MySQL。不換框架。
- 行事曆擴充既有 `GET /issues/calendar`，不另開 `/calendar`。見 Spike。
- 同日多類型：格內捲動＋截斷＋圖示區分；不上 FullCalendar。見 Spike。規格 8.5 由「待評估」改為**已確認可行**。
- 點專案議題標記：`/projects/{projectId}?item={id}` 高亮並打開編輯。
- 不調整產品範圍（無廠商、無 TODO、無綁正式議題）。
